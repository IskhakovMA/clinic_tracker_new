# Внутренний центр уведомлений

Центр уведомлений показывает пользователю персональную server-side ленту внутри
его текущего RBAC/patient scope. Внешней отправки, WebSocket, Redis, scheduler и
реальных SMS здесь нет.

## Источники

- `overdue`, `today`, `upcoming` — активные плановые события без фактического
  выполнения.
- `checklist` — незавершенные обязательные чек-листы.
- `data_quality` — только предупреждения и критичные finding из центра качества
  данных.

Информационные findings не поднимаются в уведомления. Завершенные, отмененные и
закрытые маршруты не создают новые активные уведомления по событиям.

## Хранение состояния

Активные условия вычисляются из доменных таблиц при чтении. Таблица
`internal_notification_state` хранит только состояние пользователя:

- стабильный ключ условия;
- связанный `patient_id`;
- тип и источник;
- `first_seen_at`, `last_seen_at`;
- `read_at`;
- `resolved_at`.

Стабильный ключ включает источник и дату события, поэтому перенос даты создает
новое уведомление, а прежнее условие помечается resolved. Повторное чтение
идемпотентно.

## Безопасность

- Все выборки проходят через существующий patient scope.
- Read/write endpoints требуют активную серверную сессию.
- `POST /api/internal-notifications/{id}/read` и
  `POST /api/internal-notifications/read-all` требуют CSRF token.
- Нельзя отметить уведомление пациента вне scope: ответ 404.
- Audit содержит только технические типы, source codes и patient IDs по текущей
  policy, без ФИО, телефона, диагноза, профиля клиентского пути, описаний
  findings и медицинских значений duplicate reasons.

## Интерфейс

Верхняя панель показывает колокольчик с количеством новых уведомлений. Drawer
дает быстрые фильтры: все, новые, сегодня, просрочено. Полный раздел «Центр
уведомлений» добавляет поиск, фильтр типа, статус прочтения и pagination.

Кнопка «Открыть» ведет в доступную карточку пациента на релевантную вкладку:
события, чек-лист или данные. Если уведомлений нет, показывается пустое
состояние без ошибок.


## WP-E: актуальность, повторный опрос и состояние

Календарные правила используют clock учреждения Europe/Moscow. Один расчет
читает один момент через ContextVar; вложенные расчеты аналитики, качества
данных и соответствующих ИИ-инструментов используют тот же день. Просрочка
сохраняет правило planned_date < today без факта выполнения, без отмены плана
и вне закрытого маршрута. Отсутствие нозологии не скрывает такую просрочку.
Результаты сравниваются при одинаковом scope и фильтрах, не по разным выборкам.

В памяти процесса хранится только ограниченный кэш вычисленных условий: до
8 ключей и 50000 условий суммарно. Он не хранит read_at. Ключ включает текущий
день Москвы, полный контекст доступа сотрудника и ревизию SQLite. Используется
PRAGMA data_version существующего process-wide соединения: commit из API, CLI
или другого процесса инвалидирует результат. Новое соединение после restart/
restore также дает другой ключ. Свои изменения этого соединения учитываются
через total_changes. Не подтвержденная транзакция вызывающего и другая база
никогда не публикуются в общий кэш. Расчет читает согласованный read snapshot;
commit во время расчета запрещает публикацию результата как новой ревизии.
TTL, Redis, планировщик, новые таблицы и миграции не добавлены.

После первой синхронизации служебных состояний возможен еще один пересчет:
собственный commit тоже меняет ревизию. Затем неизмененные опросы не пересчитывают
качество всей области и не выполняют INSERT/UPDATE/TEMP-вставки. Любая запись
может вызвать безопасный лишний пересчет; при частых изменениях или вытеснении
кэша выигрыша по чтению может не быть. Корректность не зависит от длительного TTL.

Состояния прочтения каждый раз читаются из базы. Синхронизация записывает только
новые, реактивированные или изменившие идентифицирующие поля условия и впервые
исчезнувшие условия. Пишущая транзакция короткая и повторно читает состояние;
конкурентное read_at не затирается. first_seen_at и история сохраняются.
last_seen_at теперь отражает создание/реактивацию/изменение состояния, а не каждый
опрос; свежесть ответа обозначает computed_at. Обычный неизмененный опрос
не изменяет last_seen_at. Список и его summary строятся из одного набора условий.

После изменения события, прав, отделения, пометки ошибочности или дня Москвы
применяются текущие данные. Кэш разных сотрудников/полномочий не смешивается;
сессионные заголовки и отбрасывание старых ответов WP-D не ослаблены.
