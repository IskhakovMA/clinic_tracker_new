# Security audit — clinic-v2.html

Дата: 2026-07-30. Объём: `clinic-tracker-python/clinic-v2.html` (единственный файл проекта — статическая HTML/CSS/JS-страница без сборщика, фреймворка, сервера и сетевых зависимостей). Метод: ручной review исходного кода (поиск источников/приёмников по методике DOM XSS) + PoC-проверка прямо в запущенной странице (без внешних сканеров/атак на посторонние системы). Референс: чек-лист `testing-for-xss-vulnerabilities` и `performing-security-headers-audit` из mukul975/Anthropic-Cybersecurity-Skills, адаптированный под фактический стек (без сервера — пункты про CSRF/CORS/API/сессии на cookie неприменимы и исключены).

## Обнаружено и исправлено

### 1. Stored/DOM XSS через несанированный вывод полей пациента — HIGH

**Проблема.** Приложение хранит пациентов в `localStorage` и рендерит их через `innerHTML` (10 точек сборки HTML-строк: `renderPatients`, `renderPatientDetails`, `renderHistoryLog`, `renderStageEventsPanel`, `renderExportPatientList`, саммари для копирования). Свободнотекстовые поля (ФИО, диагноз, телефон, врач, жалобы, заметки к этапу, а также значения дат/времени событий) подставлялись в шаблон без экранирования — как в текстовый узел (`<span>${p.name}</span>`), так и в атрибут (`value="${p.name}"`).

**Как проверялось.** Через ФИО пациента внесён payload `<img src=x onerror="...">` напрямую в состояние приложения (эквивалент правки поля через форму «Добавить пациента» или «Просмотр и редактирование данных»), вызван обычный рендер. До исправления полезная нагрузка попадала в DOM как исполняемый `<img onerror>` и сработала бы при показе карточки. Реалистичный вектор эксплуатации — не только форма редактирования (доступна любому, кто вошёл в приложение), но и функция **Импорт** JSON: `handleImportFile()` проверяет только «это массив объектов с `id`», типы и содержимое остальных полей не валидирует — вредоносный экспорт-файл, переданный коллеге («передать пациентов на время отпуска», см. `PROJECT_BRIEF.md`), исполнил бы код в его браузере при импорте.

**Затронутые места (все исправлены).** `renderExportPatientList` (имя пациента, заведующий), `renderPatients` (имя, диагноз), форма «Просмотр и редактирование данных пациента» (имя, телефон, диагноз, врач, жалобы), `renderHistoryLog` (текст события, заметка к этапу), `renderStageEventsPanel` (даты/время плана и факта, заметка к этапу — 2 текстовых поля), `renderFuturePlanEditor` (предварительные дата/время), саммари для отчётности (встраивание в HTML при показе — копирование в буфер осталось как есть, это по-прежнему открытый текст).

**Исправление.** Добавлен `app.escapeHtml()` (экранирование `& < > " '`), применён во всех перечисленных точках вывода (23 места). Сама функция `generateSummary()` не тронута (её результат также используется для копирования в буфер как есть — экранирование добавлено только в точке встраивания в HTML при показе саммари в карточке).

**Проверка.** PoC на живой странице: `patients[i].name = '<img src=x onerror="window.__xssFired=true">'` → рендер → `__xssFired` не выставился, в DOM символы вышли как `&lt;img ...&gt;` (текст, не разметка). Консоль браузера — без ошибок после правки.

**Остаточный риск.** Импорт по-прежнему не валидирует типы/формат полей (это отдельная задача — добавить схему при разборе JSON, не делалось, т.к. выходит за рамки «исправить подтверждённую XSS»); но поскольку вывод теперь везде экранируется на этапе рендера, инъекция через импорт «сырого» JSON больше не приводит к исполнению кода, независимо от того, в каком поле окажется payload.

## Проверено — проблем не найдено

- **Опасные приёмники**: `eval`, `new Function`, `document.write` — не используются нигде в файле.
- **Источники DOM XSS**: `location.hash`, `location.search`, `window.name`, `postMessage` — не читаются нигде; приложение не парсит URL и не слушает сообщения.
- **Внешние зависимости**: скриптов/шрифтов/стилей с CDN нет вообще — все шрифты (IBM Plex Sans/Mono) и логотип встроены как base64 `data:` URI, файл полностью самодостаточен (offline-first по архитектуре проекта). Supply-chain риск через сторонние JS-библиотеки отсутствует — их просто нет.
- **Ссылки/редиректы**: тегов `<a>` в файле нет вообще (все переходы — кнопки с `onclick`), соответственно `target="_blank"`/`rel="noopener noreferrer"` неприменимы.
- **Debug-код**: `console.log`, `debugger`, оставленные тестовые payload — не найдено.
- **Секреты**: хардкоженных ключей/токенов/паролей к внешним сервисам, внутренних адресов — не найдено. Единственный «пароль» — учебный `'password'`, общий для всех демо-логинов (см. ниже, это документированное ограничение, а не забытый секрет).
- **CSRF/CORS/безопасность API-запросов**: неприменимо — приложение не делает сетевых запросов и не использует cookie-based сессии (авторизация — флаг в `localStorage`).

## Известные ограничения (не исправлялось, вне рамок кода)

### Клиентская «авторизация» без реального бэкенда — по документированному дизайну
Логин (`app.login()`) — фиксированный список пользователей и один общий пароль `password`, прямо в исходнике страницы; вход через консоль браузера тривиален. Это уже зафиксировано как известное ограничение в `PROJECT_BRIEF.md` («не для реальных пациентов без доработки») и не является дефектом, внесённым в рамках этой задачи — исправление требует настоящего бэкенда с серверной аутентификацией, что вне рамок статического HTML-файла и текущей задачи.

### HTTP security headers — неприменимо в коде статического файла
CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy — это HTTP-заголовки ответа сервера; в текущей архитектуре (открытие файла напрямую или через простой статический сервер без конфигурации заголовков) их нельзя выставить из самого HTML. `<meta http-equiv="Content-Security-Policy">` технически возможен, но был осознанно не добавлен: страница держится на сотнях inline `onclick="..."` атрибутов (это архитектурная основа взаимодействия во всём файле), и CSP, реально блокирующий inline-скрипты, полностью сломает приложение; CSP с `'unsafe-inline'` для script-src, наоборот, не даёт защиты именно от того класса уязвимости, который был найден и исправлен выше — то есть создавал бы ложное чувство защищённости. Правильное решение — переход на event listeners (`addEventListener`) при следующем крупном рефакторе, а не косметический meta-тег.

**Рекомендации на уровне будущей инфраструктуры** (когда появится реальный веб-сервис, см. «Что дальше» в `PROJECT_BRIEF.md`):
- `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; object-src 'none'; base-uri 'self'; frame-ancestors 'none'` — после перехода на addEventListener (без этого `script-src 'self'` сломает все обработчики).
- `Strict-Transport-Security: max-age=31536000; includeSubDomains` — после переезда на HTTPS-хостинг.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (или CSP `frame-ancestors 'none'` дублирующе) — защита от clickjacking и MIME-sniffing.
- `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: geolocation=(), camera=(), microphone=()` — базовая гигиена, у приложения и так нет исходящих ссылок и не используются чувствительные API браузера.
- Реальная серверная аутентификация с хешированием паролей взамен текущего клиентского списка.

## Итог
Единственная подтверждённая уязвимость (XSS через несанированный вывод пользовательских данных) — исправлена и проверена. Проект не стал «полностью неуязвимым» — описанные выше ограничения (клиентская авторизация, отсутствие серверных заголовков, отсутствие валидации схемы при импорте) остаются осознанными архитектурными следствиями формата «один статический HTML-файл» и вынесены как рекомендации, а не решены в коде.
