# Security audit — clinic-v2 (frontend + backend)

Дата последнего обновления: 2026-07-30. Документ отражает состояние **после** миграции на
серверную архитектуру (FastAPI + SQLite). История первого, чисто клиентского аудита
(XSS-проход по статическому файлу от 2026-07-30 утра) сохранена в разделе «Исходные проблемы».

## Исходные проблемы (до миграции)

1. **Клиентская «авторизация»** — общий пароль `'password'` в открытом виде в исходнике,
   сравнение на клиенте, «сессия» = флаг в localStorage. Тривиально обходится через консоль.
2. **Медицинские данные в localStorage** — весь набор пациентов в незашифрованном
   localStorage браузера, без контроля целостности и доступа.
3. **Stored/DOM XSS** — найден и исправлен ещё в первом аудите (несанированный вывод
   полей пациента в `innerHTML`; добавлен `escapeHtml()` в 23 точках). Но два пробела
   оставались: неполное экранирование (`replace(/'/g ...)`) при вставке значений в
   inline-обработчики и неэкранированные `title`-атрибуты в `renderHeads`/`renderExportHeadsFilter`.
4. **Импорт без валидации** — `handleImportFile` проверял только «это массив с id»;
   вредоносный экспорт-файл мог перезаписать данные и внедрить произвольные структуры.
5. **Отсутствие security headers** — статический файл, заголовки выставлять некому.
6. **Нет CSRF-защиты, нет rate limiting, нет сессий** — не к чему было применять.

## Реализованная архитектура

- **Стек**: FastAPI 0.141 + Pydantic 2 + SQLite (stdlib `sqlite3`) + Argon2id (`argon2-cffi`) + pytest.
- **Один процесс** отдаёт и API (`/api/*`), и статический frontend (`/`, `/clinic-v2.js`) —
  same-origin, поэтому CORS-мидлвари нет вовсе (нечего разрешать).
- **Слушает только 127.0.0.1** по умолчанию; debug выключен; `/api/docs` доступен только в debug.
- **Схема БД**: `patients` / `history_entries` / `events` / `future_plans` (FK с каскадом,
  NOT NULL, UNIQUE(seq)), `sessions`, `app_login`, `schema_version`. Чек-лист хранится
  JSON-колонкой на `history_entries` — осознанная денормализация: ключи чек-листа это
  свободный текст из справочника нозологий, не реляционные сущности.
- **Идентификаторы** — серверные UUID4. Клиентский `id` никогда не назначает идентичность:
  создание всегда генерирует новый, импорт в режиме «обновить» лишь сопоставляет с уже
  существующими на сервере записями.

## Модель авторизации и сессий

- Один пароль приложения. Задаётся `python -m backend.cli set-password` (или env-переменной
  только при первом запуске). Хранится **только** Argon2id-хеш (не SHA-256/MD5), сравнение
  на сервере, хеш клиенту не отдаётся никогда.
- Сессия — случайный opaque-токен; в БД хранится **SHA-256-хеш токена** (кража файла БД не
  даёт готовых сессий). Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS-режиме,
  `Path=/`, TTL 8ч. Токен ротируется при каждом логине; logout удаляет запись на сервере.
- Ошибка входа — единое сообщение без деталей. Rate limiting: 5 неудач за 15 минут → 429 c
  экспоненциальным backoff и `Retry-After` (in-memory, сбрасывается при рестарте процесса —
  задокументированное ограничение, адекватное одиночному локальному процессу).
- **Каждый** `/api/*`-endpoint (кроме login/me) требует валидную сессию на сервере;
  скрытие кнопок в UI механизмом доступа не считается.

## CSRF

Все изменяющие запросы (POST/PUT/PATCH/DELETE, включая импорт и миграцию) требуют заголовок
`X-CSRF-Token`, совпадающий с токеном, привязанным к серверной записи сессии (выдаётся
отдельной не-HttpOnly cookie при логине). GET-запросы данных не изменяют (проверено тестом).
`TrustedHostMiddleware` дополнительно отсекает запросы с чужим Host.

## Валидация

Pydantic-модели на каждый вход: пациент, поле пациента, событие, заметка, чек-лист,
предварительный план, документ импорта. Ограничения: ФИО/врач/заведующий ≤200, телефон ≤50,
диагноз ≤500, жалобы/заметки ≤5000, возраст 0–150, приоритет/этап/стадия/тип лечения — enum,
даты — ISO `YYYY-MM-DD`, нормализация пробелов. Frontend-валидация осталась только для
удобства; сервер повторяет все проверки.

## Импорт и экспорт

**Импорт** — двухфазный (`/api/import/preview` → подтверждение пользователем с выбором
режима → `/api/import/commit`), режимы: добавить / обновить совпадающие / полная замена
(режим по умолчанию — безопасный «добавить»; «полная замена» требует дополнительного
подтверждения). Отклоняются: не-JSON, неверный корень, неизвестная schemaVersion, >500
записей, >5 МБ, неверные типы/enum/даты, дубли id, ключи `__proto__`/`constructor`/`prototype`,
превышения длин. Ошибки возвращаются списком с номером записи и полем, без stack trace.
Частично-валидный набор не импортируется вообще; запись — одна транзакция с rollback
(проверено тестом с искусственным сбоем посередине).

**Экспорт** — только через backend после авторизации: `{schemaVersion, generatedAt, patients}`,
безопасное имя файла, корректный Unicode/кириллица (`ensure_ascii=False`). Тест закрепляет
отсутствие в экспорте паролей/хешей/сессий/CSRF/путей сервера. Перед экспортом UI показывает
предупреждение о чувствительности данных. Шифрованный экспорт не реализован (см. ограничения).

**Миграция из localStorage** — отдельный одноразовый маршрут: только по явному действию
пользователя (баннер появляется лишь когда на сервере пусто, а в браузере есть старые данные),
preview с количеством записей → подтверждение → атомарный перенос; локальная копия удаляется
только после успеха и отдельного согласия. При занятой базе — 409.

## XSS и DOM (переработано на этапе 3)

Первый этап полагался на экранирование HTML-строк. Теперь строки HTML вообще не собираются:

- **`innerHTML` — 11 → 0.** Все точки рендера переписаны на `document.createElement` /
  `textContent` / `replaceChildren` / `DocumentFragment` через общие хелперы `el()`,
  `frag()`, `option()` в `clinic-v2.js`. Значение пользовательского поля попадает в DOM
  только через `textContent` или `.value` и не может быть интерпретировано как разметка.
  `outerHTML` / `insertAdjacentHTML` / `document.write` / `eval` / `new Function` — 0.
- **Функции экранирования удалены.** `escapeJsAttr()` существовала только чтобы протаскивать
  значения в inline-обработчики — удалена вместе с ними. `escapeHtml()` после отказа от
  HTML-строк стала мёртвым кодом и тоже удалена. Новых аналогов не вводилось: там, где
  значение не интерпретируется как HTML, экранирование не нужно.
- **Идентификаторы вместо данных.** Обработчики получают `patient.id` (серверный UUID),
  индексы и имена полей через замыкания; ФИО, диагнозы, жалобы, врачи, заметки в `data-*`
  и в JS-контекст не попадают. Имя чек-лист-пункта и ФИО заведующего передаются замыканием,
  а не через атрибут.
- URL-контекстов с пользовательскими данными нет (в приложении вообще нет `<a href>`);
  `javascript:`/`data:`-схемы неоткуда взять.
- **PoC в работающем приложении** (payloads из ТЗ, локально, без внешних запросов):
  `<img src=x onerror="window.__xssFired=1">` в поле жалоб — сохранён через API, отрисован
  в карточке и в форме редактирования как текст, `<img>` в DOM не создан, обработчик не
  исполнился, `window.__xssFired` не выставлен. API-тесты (`test_xss_api.py`) закрепляют
  неизменный round-trip payload'ов через создание/экспорт/импорт; статические тесты
  (`test_frontend_csp.py`) падают, если `innerHTML` или inline-обработчик вернутся в код.

## Inline JavaScript устранён

Было ~60 атрибутов `onclick=`/`onchange=`/`oninput=`/`onkeydown=` (16+6 в статическом HTML,
17+25 в шаблонах JS) — стало **0**. Взамен: статическая разметка получила `id` и слушатели
через `addEventListener` в конце `clinic-v2.js`; динамические элементы создаются с
обработчиками, привязанными при создании (замыкание над id/индексом). Клавиатурная
доступность узлов таймлайна (Enter/Space) сохранена и проверена, добавлено закрытие
модальных окон по Escape. Единственное место, где inline-обработчики остались, — устаревший
автономный `clinic.html` (прежний дизайн, ожидает решения пользователя; в этом этапе не
трогался и остаётся байт-в-байт как в baseline).

## CSP и security headers (выставляются сервером, проверены тестами)

Итоговая политика:

```
default-src 'self'; script-src 'self'; script-src-attr 'none'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; font-src 'self' data:; connect-src 'self'; object-src 'none';
base-uri 'self'; frame-ancestors 'none'; form-action 'self'
```

- **Inline JavaScript запрещён полностью**: нет `unsafe-eval`, нет `script-src 'unsafe-inline'`,
  а `script-src-attr 'none'` запрещает и обработчики-атрибуты (было `'unsafe-inline'`).
  JS грузится единственным same-origin файлом `clinic-v2.js`.
- **Остаётся `style-src 'unsafe-inline'`** — документированное ограничение: разметка построена
  на inline `style=`-атрибутах (это дизайн-решение первого этапа, а не JS). Разрешение inline
  CSS не даёт исполнения скриптов и не эквивалентно `script-src 'unsafe-inline'`; вынос стилей
  в файл — задача этапа UI/UX, не этого.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy: geolocation=(), camera=(), microphone=()`, `Cache-Control: no-store`
  на всех `/api/*`. HSTS — **только** при `CLINIC_HTTPS=true`, фиктивного HSTS на HTTP нет.
- `TrustedHostMiddleware` ограничивает Host до localhost; CORS-мидлвари нет вовсе.

## Аудит действий

Таблица `audit_events` (`id`, `created_at`, `event_type`, `actor`, `patient_id`, `result`,
`request_id`, `detail`), модуль `backend/app/audit.py`.

**Записывается**: успешный/неуспешный вход, срабатывание rate-limit, выход, смена пароля,
создание/изменение/удаление пациента (включая смену этапа), import preview, подтверждённый
импорт с режимом и счётчиками, экспорт с числом записей, миграция из localStorage, backup,
restore, провал проверки целостности БД.

**Никогда не записывается**: пароли, password hash, session token, CSRF-токен, cookie, ФИО,
телефон, диагноз, жалобы, врач, заметки, содержимое импорта/экспорта, медицинские записи.
В `detail` попадают только неконфиденциальные метаданные — имя изменённого поля (не значение),
режим импорта, счётчики. Закреплено тестом, который ищет в журнале конкретные маркеры
(пароль, имя пациента, телефон, диагноз, жалобы, врач, значения полей, токены сессии/CSRF).

**Actor** — необратимый 16-символьный отпечаток от *хеша* сессионного токена: позволяет
связать события одной сессии, но не восстановить сессию (проверено тестом, что actor не
содержит токен и наоборот). `patient_id` — серверный UUID, персональных данных не несёт.

**Политика при сбое — fail-open** (осознанно и задокументировано): исключение при записи
аудита проглатывается и логируется без payload, клиническая операция продолжается. Для
однопользовательского локального инструмента потеря строки журнала менее вредна, чем отказ
сохранить дату лечения пациента. Проверено тестом: удаление таблицы аудита не ломает
создание пациента. При переходе к многопользовательскому или сетевому режиму это решение
нужно пересмотреть в пользу fail-closed для security-событий.

**Просмотр и хранение**: `GET /api/audit?limit&offset` (требует сессию, лимит ≤200) или
`python -m backend.cli audit-tail`. Срок хранения — 365 дней (`CLINIC_AUDIT_RETENTION_DAYS`),
очистка вручную: `python -m backend.cli audit-prune`. Автоматического удаления нет.

## Жизненный цикл сессий

- Токен ротируется при каждом входе; значение cookie, присланное клиентом до входа, не
  становится сессией (session fixation невозможен — проверено тестом).
- В БД хранится только SHA-256 токена; исходный токен не попадает ни в базу, ни в логи,
  ни в аудит (тест сверяет дамп БД и журнал).
- Истечение: идле/абсолютный TTL 8ч. Предъявление истёкшего токена → 401 **и** удаление
  строки. Плюс очистка при каждом входе и команда `purge-sessions`. Отдельный планировщик
  не вводился.
- Выход: удаление серверной записи + сброс обеих cookie (`Max-Age=0`).
- **Смена пароля инвалидирует все активные сессии** (`DELETE FROM sessions` в одной
  транзакции с обновлением хеша) — проверено тестом.
- Одинаковый безопасный ответ 401 для отсутствующей, истёкшей и поддельной сессии.
- `Cache-Control: no-store` на всех authenticated-ответах (проверено для
  `/api/patients`, `/api/export`, `/api/audit`, `/api/auth/me`).

## Fail-closed конфигурация

Пароля по умолчанию нет: при отсутствии env-переменной и сохранённого хеша вход невозможен
(503 «пароль не настроен»), никакой встроенной учётки admin/password не существует —
проверено тестом, который перебирает очевидные пароли на неинициализированной базе. Слабый
пароль в `CLINIC_ADMIN_PASSWORD` не принимается при bootstrap (вход остаётся невозможным).
Смена пароля через CLI: скрытый ввод, подтверждение, минимум 8 символов, отклонение очевидных
паролей (`password`, `12345678`, …), пароль не печатается, пересоздаётся Argon2id-хеш, все
сессии завершаются, пишется обезличенное событие аудита. Debug выключен, `/api/docs` и
`/redoc` — 404, traceback клиенту не уходит (единый `{"error": "Internal server error"}`),
слушаем только 127.0.0.1, wildcard-CORS нет, база/бэкапы/`.env` по HTTP недоступны (404),
`.env.example` не содержит секретов, `.gitignore` покрывает базу, WAL/SHM, бэкапы, логи и `.env`.

## SQLite: целостность, backup, restore

- На каждом соединении: `PRAGMA foreign_keys = ON`, `journal_mode = WAL`,
  `busy_timeout = 5000` (ожидание вместо мгновенной ошибки при конкурентной записи).
- Все запросы параметризованы; SQL из пользовательских строк не собирается (имена колонок
  берутся из белых списков `FIELD_COLUMN`/`EVENT_FIELD_COLUMN`, не из ввода).
- Транзакции с rollback (проверено искусственным сбоем посреди импорта), каскадное удаление,
  индексы на FK и часто используемые поля поиска (`name`, `head`, `stage`, `expires_at`,
  `created_at`), версия схемы, идемпотентная инициализация (`CREATE TABLE IF NOT EXISTS`).
- `python -m backend.cli check-db` — `integrity_check`, `foreign_key_check`, версия схемы,
  наличие обязательных таблиц; сначала применяет идемпотентную инициализацию (как при старте
  приложения), чтобы база предыдущей версии была дообновлена; `--no-migrate` проверяет файл
  как есть. Медицинские данные не печатает — только счётчики и результаты проверок.
- `python -m backend.cli backup` — через **SQLite backup API** (не копирование файла),
  корректно при WAL, имя с датой, каталог вне static-директории, отказ перезаписать
  существующий файл без `--overwrite`, права 600 (POSIX), событие аудита, печать пути.
- `python -m backend.cli restore <file>` — проверка существования → магии `SQLite format 3`
  → `integrity_check` → версии схемы → обязательных таблиц → **бэкап текущей базы** →
  явное подтверждение (`--yes` для автоматизации) → запись во временный файл и атомарная
  подмена (`Path.replace`) → удаление устаревших WAL/SHM → событие аудита. Повреждённая или
  несовместимая копия отклоняется, текущая база не изменяется (проверено тестами).
  На Windows `chmod` не применяется — конфиденциальность обеспечивается ACL и шифрованием диска.
- `backend/scripts/backup_db.sh` оставлен тонкой обёрткой над Python-командой.

## Логи и ошибки

В логи не пишутся пароли, cookie, session id, CSRF-токены и содержимое медицинских записей.
Клиент получает единый безопасный формат ошибки; stack trace — только в серверном логе.
Debug-режим выключен по умолчанию.

## База и резервные копии

Файл БД лежит в `backend/data/` — каталог не раздаётся по HTTP (тест: 404 по всем путям),
исключён из Git вместе с `.env`, бэкапами и логами. Команды backup/restore описаны выше.
Шифрование БД на уровне приложения не реализовано намеренно — см. ограничения.

## Зависимости

`pip-audit -r backend/requirements.txt` от 2026-07-30: **No known vulnerabilities found**.
В процессе: начальный пин fastapi 0.115/starlette 0.41 имел известные уязвимости
(PYSEC-2026-161 и др.) — поднято до fastapi 0.141.1/starlette 1.3.1; `python-multipart`
удалён как неиспользуемый (импорт идёт JSON-телом, форм-загрузок нет). Версии зафиксированы.

## Остаточные ограничения

- **Локальная однопользовательская архитектура**: нет ролей и разграничения доступа между
  сотрудниками. Аудит фиксирует действия по обезличенной сессии, а не по конкретному
  сотруднику — при одном общем пароле различить людей невозможно by design.
- **SQLite не зашифрован приложением** — конфиденциальность файла на диске должна
  обеспечиваться полным шифрованием диска (FileVault/BitLocker/LUKS) и правами ОС. На Windows
  права файла через `chmod` не выставляются — только ACL и шифрование диска.
- **Шифрованный экспорт не реализован** — стандартной надёжной библиотеки в стеке нет,
  самодельная криптография не писалась. Экспорт-файл открытый; UI предупреждает об этом.
- **Rate limiting в памяти процесса** — сбрасывается при рестарте; для локального
  единственного процесса признано достаточным.
- **`style-src 'unsafe-inline'`** остаётся в CSP — разметка построена на inline `style=`;
  это не даёт исполнения скриптов, вынос стилей — задача этапа UI/UX.
- **Аудит fail-open** — при сбое записи журнала операция продолжается (обосновано выше);
  для многопользовательского/сетевого режима требуется пересмотр.
- **Очистка аудита и истёкших сессий — ручная** (CLI), автоматического планировщика нет.
- **Сетевое развёртывание требует HTTPS reverse proxy** (см. README) — в HTTP-режиме cookie
  не имеют Secure-флага, HSTS выключен.
- **Устаревший `clinic.html`** (прежний автономный дизайн) сохраняет клиентский пароль и
  inline-обработчики — он не входит в состав защищённого приложения и ожидает решения
  пользователя; при выборе этого дизайна всю работу этапов 2–3 нужно переносить в него.
- **Нет медицинской сертификации** — приложение не проходило сертификацию как медицинское
  изделие/МИС; применение для реальных пациентов требует соответствия локальным
  регуляторным требованиям (см. также ограничения в `PROJECT_BRIEF.md`).
- Исправлены подтверждённые проблемы и проверены перечисленные сценарии; это не утверждение,
  что «все уязвимости исключены».
