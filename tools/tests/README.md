# Браузерные проверки WP-D

Зависимости тестового окружения: Python с backend/requirements-dev.txt, Node.js,
Playwright и Chromium. Playwright не является зависимостью рабочего приложения.
Ничего из этих проверок не отправляется на GitHub или внешнему API.

Из корня worktree:

```sh
node tools/tests/wp_d_browser.cjs
```

Этот сценарий поднимает временный HTTP-сервер на loopback и подменяет только API
в Playwright. Проверяются HTTP-ошибки, сеть, тайм-аут, повторный вход, другой
сотрудник, отсутствие автосохранения, версии, Escape/закрытие формы, debounce,
ответы поиска в обратном порядке и 429. Время тайм-аута управляется часами браузера;
для порядка ответов используются явно удерживаемые ответы, без sleep и retry.

Для настоящего backend запустите отдельный стенд:

```sh
python tools/tests/wp_d_synthetic_server.py --port 18427
```

Стенд всегда создает новый временный каталог базы, игнорируя прежний
CLINIC_DATA_DIR. Учетная запись и пароль синтетические, только для этого стенда.
Во втором терминале:

```sh
WP_D_SYNTHETIC_ORIGIN=http://127.0.0.1:18427 node tools/tests/wp_d_live_browser.cjs
```

Не направляйте WP_D_SYNTHETIC_ORIGIN на рабочий сервер: сценарий создает тестовые
карточки, завершает тестовую сессию и выполняет синтетические правки.

Если Playwright установлен вне обычного пути Node, задайте PLAYWRIGHT_MODULE
(путь к пакету). Для имеющегося Chromium задайте BROWSER_EXECUTABLE (путь к файлу).
Необязательный WP_D_SCREENSHOT задает путь для снимка синтетического черновика.
Стенд останавливается Ctrl+C; созданный временный каталог можно удалить после
проверки. Рабочая база и существующие учетные записи в тестах не используются.

## WP-D FIX1

На том же новом синтетическом стенде:

```sh
WP_D_SYNTHETIC_ORIGIN=http://127.0.0.1:18427 node tools/tests/wp_d_fix1_browser.cjs
```

Сценарий создает отдельные тестовые учетные записи и подразделения через API.
Проверяются отзыв доступа через роль/подразделение, сохраненный доступ и старые
версии черновика, переход в read-only, две вкладки одной cookie-сессии,
отсутствие BroadcastChannel, прямой неожиданный запрос записи и удержанный
старый ответ, полученный до переключения сотрудника. Все изменения — только
на синтетическом сервере. Выполнять против рабочей базы запрещено.

## WP-D FIX2

На отдельном синтетическом стенде выполните:

```sh
WP_D_SYNTHETIC_ORIGIN=http://127.0.0.1:18427 node tools/tests/wp_d_fix2_browser.cjs
```

Проверяются свежие диагноз, версия, телефон, маршрут и событие после повторного
входа без черновика и с отдельным черновиком (в том числе ввод до blur), настоящий
409 при ручной отправке прежней версии и успешная ручная запись неизмененной
карточки. Клиническая дата проверяется через реальный changeStage: без
автоподтверждения, с успешным ручным подтверждением и с 409 после внешней правки
события. Дополнительно сохраняется ввод нового пациента. Старые live/FIX1
проверки остаются обязательными; все API-записи выполняются на временной базе.


## WP-E: время и уведомления

Целевые регрессии:

```sh
python -m pytest backend/tests/test_wp_e_time_notifications.py backend/tests/test_wp_e_overdue_inbox.py -q
```

Отдельный стенд всегда создает новую временную базу и использует mock:

```sh
python tools/tests/wp_e_synthetic_server.py --port 18435 --now 2026-10-01T11:00:00+03:00
WP_E_SYNTHETIC_ORIGIN=http://127.0.0.1:18435 node tools/tests/wp_e_browser.cjs
```

Проверяются реальные API и браузерные пояса America/Los_Angeles/Asia/Tokyo:
серверное значение по умолчанию, ручное время МСК, UTC в очереди, preview,
литеральные скобки и безопасный отказ при недопустимом шаблоне. Для обычных
браузерных регрессий WP-D используйте отдельный wp_d_synthetic_server.py:
клинические даты этих сценариев проверяются его обычными часами учреждения.
Playwright/Chromium задаются переменными из инструкции выше; новые пакеты не нужны.
Не направляйте эти сценарии на рабочий сервер. В тестах часы внедряются внутри
изолированного Python-процесса; системное время и глобальные настройки не меняются.


Ручной замер AUD-31 (4000 синтетических пациентов, настоящий TestClient,
trace SQL всех используемых соединений):

```sh
WP_E_METRICS_JSON=/tmp/wp-e-metrics.json python -m pytest tools/tests/wp_e_metrics.py -q -s
```

До и после используйте один и тот же файл сценария, одинаковый Python и
отдельные временные базы. Для исходного SHA выполните сценарий из каталога
его git archive, указав этот каталог в PYTHONPATH. Сохраняются холодный и два
повторных запроса: SQL statements, total_changes (включая TEMP), время HTTP-
обработки и длительность транзакции, которая пишет main-состояние. Read-only
BEGIN не считается пишущей транзакцией. Замер не входит в обычный набор CI.
