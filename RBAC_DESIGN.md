# RBAC: роли, области видимости и разграничение доступа

Документ описывает модель контроля доступа «Системы планирования»
(актуальная схема БД v3). Все проверки выполняются **на backend** в централизованном
слое `backend/app/policy.py`; скрытие кнопок во frontend — только
согласование интерфейса с правами, а не защита.

## Роли

| id роли | Название | Стратегия scope |
|---|---|---|
| `developer` | Разработчик | `global` |
| `deputy_chief_oncology` | Заместитель главного врача по онкологии | `global_readonly` |
| `caop_head` | Заведующий ЦАОП | `global_readonly` |
| `department_head` | Заведующий отделением | `by_department` |
| `doctor` | Врач | `by_treating_doctor` |
| `consilium_chair` | Председатель онкологического консилиума | `by_treating_doctor` |

Справочник ролей хранится в таблице `roles` и наполняется автоматически.
Архитектура не ограничена этими пятью ролями: новая роль — это запись в
`roles` плюс, при необходимости, новая стратегия scope в `policy.py`.

### Председатель онкологического консилиума

- Область видимости карточек — обычная `by_treating_doctor`: только пациенты,
  у которых председатель указан лечащим врачом.
- Записи консилиума председатель видит через `/api/consilium/*` целиком
  (все записи, сетка, реестры, аналитика председателя) — это данные,
  необходимые для заседания: ФИО, полис ОМС, диагнозы, назначения.
- **Избранное — закладка внутри консилиума.** Оно не расширяет
  `patient_scope_filter`: карточка, её подресурсы, ИИ-инструменты, уведомления,
  качество данных и общая аналитика для такого пациента остаются недоступны (404).
- Импорт и массовый экспорт пациентов председателю недоступны; реестры XLSX —
  только председателю и разработчику, с X-CSRF-Token, лимитом 20/мин и аудитом
  `consilium_registry_exported` без ПДн.
- Решения: `recorded → in_review` (явное «Начать рассмотрение»),
  `in_review → signed`, возврат на доработку — из любого неподписанного и не
  архивного состояния. Повторная подпись и возврат подписанного решения
  запрещены (409); подписанная запись неизменна и на уровне БД (триггер
  `trg_consilium_signed_immutable`; меняются только архив врача и отметка о
  хирургическом направлении). Отзыв подписи не реализован.
- Врач правит и удаляет свою запись, пока председатель не начал рассмотрение.
- Расписание: чужая запись в слоте видна врачу только как «занято»; детали —
  автору записи, пока пациент в его области, и председателю.
- Запись на консилиум не меняет этап маршрута пациента; правила связи решения
  с маршрутом не согласованы и не реализованы.

## Области видимости (scope)

Единственный источник правила видимости пациента —
`policy.patient_scope_filter(user)`, возвращающий SQL-условие. Оно
применяется ко **всем** выборкам: списку, поиску, фильтрам, статистике,
календарю, карточке по ID, вложенным endpoints (события, чек-листы,
заметки, планы, история), экспорту и проверкам импорта. Обхода через
другой endpoint нет, потому что другого пути к пациентам нет.

- `global` — все пациенты, включая несопоставленных; полный CRUD.
- `global_readonly` — все пациенты, только чтение; любые POST/PATCH/PUT/DELETE
  отклоняются с 403.
- `by_department` — пациенты, чей лечащий врач (по `treating_doctor_user_id`)
  состоит в **активных** отделениях, которыми управляет заведующий
  (`department_heads`). Заведующий нескольких отделений видит объединение;
  цепочка: пациент → лечащий врач → отделения врача → пересечение с
  отделениями заведующего.
- `by_treating_doctor` — только пациенты, где
  `treating_doctor_user_id = текущий пользователь`. Врач **не видит**
  пациентов коллег даже своего отделения.

Недоступный пациент неотличим от несуществующего: единый ответ 404 без
деталей. Для видимого, но нередактируемого (read-only роли) — 403.

## Матрица доступа (сводно)

| Действие | developer | global read-only | department_head | doctor |
|---|---|---|---|---|
| Просмотр пациентов | все | все | свой scope | только свои |
| Создание пациента | любой врач или unresolved | нет | врач своего отделения | только за собой |
| Изменение/удаление | все | нет | свой scope | только свои |
| Смена лечащего врача | да | нет | нет | нет |
| Импорт | add/update/replace | нет | add, врач своего отделения | add, за собой |
| Экспорт | всё | нет | свой scope | только свои |
| Сотрудники и роли | да | нет | нет | нет |
| Отделения и состав | да | нет | нет | нет |
| Системный аудит | да | нет | нет | нет |
| Качество данных | все + unresolved | все, read-only | свой scope | только свои |

Экспорт — отдельное permission (`can_export`), а не следствие чтения:
глобальным read-only ролям массовый экспорт не предоставляется.

## Центр качества данных

`/api/data-quality/summary`, `/api/data-quality/issues` и
`/api/data-quality/patients/{id}` используют тот же
`policy.patient_scope_filter`, что и список и карточка пациента. Раздел не
добавляет новых write-прав: он только показывает вычисленные backend-проблемы и
ведёт в существующую карточку пациента или, для Разработчика, в уже существующий
workflow сопоставления несопоставленного лечащего врача.

- `developer` видит качество всех пациентов, unresolved-записи и глобальные
  duplicate-группы внутри полного scope.
- `deputy_chief_oncology` и `caop_head` видят глобальный summary и проблемы
  только для чтения; suggested actions помечены как недоступные для записи.
- `department_head` видит качество только пациентов врачей своих активных
  отделений и не получает сведений о пациентах других отделений.
- `doctor` видит только своих пациентов; возможные дубли строятся только среди
  его доступных записей.

Query-параметры фильтров не расширяют scope. Прямой запрос к недоступному
`patient_id` сохраняет единый безопасный 404, а фильтр по недоступному ID
возвращает пустой результат без подтверждения существования записи.

## Связи врача и заведующего с отделениями

- `user_departments` — членство врача в отделениях (может быть несколько).
- `department_heads` — управление заведующего отделениями; один заведующий
  может управлять несколькими отделениями, у отделения — один заведующий.
- Если врач состоит в нескольких организационных единицах, scope
  заведующего определяется пересечением активных связей врача и заведующего.
- Архивированное отделение (`departments.status = 'archived'`) выпадает из
  всех scope-вычислений; физическое удаление отделений не предусмотрено.

### Перевод врача между отделениями

Доступ заведующих к пациентам определяется **текущим** отделением
**текущего** лечащего врача — scope вычисляется по актуальным связям при
каждом запросе, кэша прав нет. Поэтому после перевода врача (удаление из
одного отделения, добавление в другое):

- заведующий прежнего отделения немедленно теряет доступ к пациентам
  этого врача;
- заведующий нового отделения немедленно его получает;
- сам врач продолжает видеть своих пациентов независимо от отделения.

История членства врача в отделениях на текущем этапе **не хранится** —
только безопасное обновление текущей связи (пациенты и их данные при
переводе не затрагиваются). Исторические срезы «кто где работал» — вне
рамок этапа.

## Смена лечащего врача

Выполняется только Разработчиком (`PUT /api/patients/{id}/treating-doctor`)
с подтверждением в интерфейсе. Пациент не копируется — меняется
закрепление. Поскольку scope вычисляется на каждый запрос:

- прежний врач и его заведующий теряют доступ немедленно;
- новый врач и его заведующий получают доступ немедленно;
- глобальные роли и Разработчик продолжают видеть пациента;
- событие фиксируется в аудите (`treating_doctor_changed`).

## Несопоставленные legacy-врачи (unresolved)

После миграции v1→v2 у существующих пациентов лечащий врач остаётся
текстом (`patients.doctor`), а `treating_doctor_user_id` пуст. Такие
пациенты:

- видны Разработчику и глобальным read-only ролям;
- не видны врачам и заведующим, пока сопоставление не выполнено;
- перечислены в `GET /api/patients/unresolved` — просмотр списка доступен
  Разработчику и обеим глобальным read-only ролям (200), заведующим и
  врачам — 403; **сопоставление** (`PUT /api/patients/{id}/treating-doctor`)
  доступно только Разработчику;
- отображаются в разделе «Структура»
  («Несопоставленные лечащие врачи»), где Разработчик вручную выбирает
  учётную запись. Автоматическое сопоставление по ФИО намеренно не
  выполняется (неоднозначность недопустима).

Legacy-текст врача сохраняется и после сопоставления обновляется на ФИО
учётной записи. Изменять текстовое поле `doctor` могут только Разработчики.

## Административные действия

Только Разработчик: создание/изменение учётных записей, назначение ролей,
блокировка/деактивация/восстановление, сброс паролей, завершение сессий,
создание/переименование/архивирование отделений, назначение заведующих,
состав отделений, смена лечащего врача, полный импорт/экспорт, системный
аудит. Все действия пишутся в аудит с `actor_user_id`/`actor_role` и
`target_user_id`/`target_department_id` (без ФИО и медицинских данных).

## Уведомления

Уведомления используют тот же patient scope, что список и карточка пациента.

- `developer`: видит все уведомления, меняет согласие, управляет шаблонами,
  запускает генерацию/worker, отменяет и повторяет failed-уведомления.
- `deputy_chief_oncology` и `caop_head`: видят уведомления и настройки согласия
  доступных пациентов только в режиме просмотра; write endpoints возвращают 403.
- `department_head`: видит пациентов врачей своих активных отделений, может
  фиксировать согласие и создавать/отменять напоминания только в своём scope.
- `doctor`: видит и меняет уведомления только своих пациентов.

Query-фильтры `doctor`, `department`, `patient_id`, `search` не расширяют scope:
сервер всегда добавляет `policy.patient_scope_filter`. Чужой notification ID и
чужой patient ID возвращают безопасный 404/пустую выдачу.

Блокировка, деактивация, сброс пароля и критическое изменение роли
немедленно завершают активные сессии пользователя (`sessions.user_id`).
Статус и роль перечитываются из БД на каждый запрос, поэтому изменения
прав действуют без ожидания истечения сессии.

## Будущее расширение: патоморфологи и доступ с этапа лекарственной терапии

Зафиксировано намерение, **без реализации на текущем этапе**:

- позднее появится отдельная роль/группа доступа для патоморфологов;
  их права и область видимости будут определены отдельно;
- для химиков (сотрудников лекарственной терапии) пациент должен
  становиться доступен **не сразу, а с момента начала лекарственной
  терапии** — то есть появится ограничение по этапу маршрута, а не только
  по врачу и отделению.

Централизованная политика к этому готова: стратегия scope — это ветка в
`patient_scope_filter` плюс запись в `roles.scope_strategy` (например,
`by_treatment_stage` или комбинация роль+подразделение+этап). Endpoints
не содержат ролевых проверок и переписываться не будут. Сейчас stage-based
логика, роли патоморфолога/химика и какие-либо скрытые permissions для них
намеренно отсутствуют и в интерфейсе не показываются.
