# Система планирования

Трекер маршрута онкопациентов (первичный приём → обследование → консилиум → лечение) для МКНЦ.
Backend — FastAPI + SQLite, frontend — статические файлы, которые отдаёт тот же сервер.

## Возможности

- Ведение карточек пациентов, маршрута лечения, событий, чек-листов и будущих
  планов.
- Персональная запись доступных врачу пациентов на онкологический консилиум:
  тестовые свободные слоты, консилиумные группы, диагнозы C00–C97 и
  редактирование созданных записей.
- Роль председателя онкологического консилиума: общий календарь записей,
  статусы рассмотрения, возврат врачу с комментарием, подписание решения с
  назначенным лечением и отдельная аналитика загрузки и назначений.
- Импорт, экспорт, резервное копирование и проверка целостности локальной базы.
- Персональные учётные записи, RBAC и серверная область доступа пациентов.
- Раздел **«Качество данных»**: backend-правила находят неполные поля,
  ошибки дат, незавершённые обязательные чек-листы, несопоставленного врача и
  возможные дубли внутри доступной области. Подробности — в
  [DATA_QUALITY.md](DATA_QUALITY.md).
- Раздел **«Уведомления»**: отдельное согласие на SMS, ожидающие напоминания,
  безопасные системные шаблоны, отправка через тестовый provider и
  статусы отправки без реальных SMS. Подробности — в
  [NOTIFICATIONS.md](NOTIFICATIONS.md).
- **Внутренний центр уведомлений**: персональная лента просроченных,
  сегодняшних и ближайших событий, незавершённых чек-листов и критичных
  проблем качества данных, а также ручных отметок «требует внимания» внутри текущей области доступа RBAC. Состояние
  «прочитано» хранится server-side; внешних отправок нет. Подробности —
  в [INTERNAL_NOTIFICATION_CENTER.md](INTERNAL_NOTIFICATION_CENTER.md).
- **Пациент требует внимания**: отдельная сущность `Patient Attention Issue`
  с lifecycle `open/closed`, причиной, коротким комментарием, автором,
  датой создания и историей закрытия. Это ручная управляемая отметка, а не
  автоматическое превращение overdue/Data Quality finding в задачу.
- Раздел **«Аналитика»**: визуальный dashboard для руководящих ролей и
  администратора с KPI, распределением по этапам и профилям клиентского пути,
  состоянием маршрутов, явными пациентами, требующими внимания, проблемами
  качества данных, динамикой и нагрузкой врачей. Данные считаются server-side
  внутри текущей области доступа RBAC.
- **ИИ-помощник V1**: встроенный read-only drawer для свободных вопросов по
  доступным данным, Attention, просрочкам, внутренним уведомлениям и Analytics
  V2. По умолчанию выключен, настраивается только backend-переменными для
  OpenAI-compatible local/internal provider, историю не сохраняет. Подробности —
  в [AI_ASSISTANT_V1.md](AI_ASSISTANT_V1.md).

### Оформление

Две полноценные темы — тёмная и светлая. Переключаются кнопкой в верхней панели
или в разделе «Настройки», без перезагрузки страницы. Выбранная тема — единственное,
что приложение сохраняет в браузере; медицинские данные и токены там не хранятся.

## Установка

Требуется Python 3.11+.

```bash
cd clinic-tracker-python
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt        # рантайм
pip install -r backend/requirements-dev.txt    # + тесты и pip-audit
```

## Учётные записи и первый Разработчик

Общего пароля больше нет: у каждого сотрудника — персональная учётная
запись (логин + пароль, Argon2id-хеш в базе) и роль с областью видимости
пациентов. Модель доступа описана в [RBAC_DESIGN.md](RBAC_DESIGN.md).

Первый Разработчик создаётся из терминала:

```bash
python -m backend.cli create-developer
```

Команда запрашивает логин, ФИО и пароль (скрытый ввод с подтверждением —
пароль не передаётся аргументом и не попадает в shell history), не создаёт
дубликаты логинов и требует явного подтверждения для второго Разработчика.
Пока ни одной учётной записи нет, вход невозможен — паролей по умолчанию
в приложении не существует.

Дальше сотрудники создаются Разработчиком в разделе «Сотрудники»:
временный пароль показывается один раз, при первом входе сотрудник обязан
сменить его на собственный.

### Миграция со старого общего входа

1. Сделайте резервную копию: `python -m backend.cli backup`.
2. Обновите код и запустите приложение — схема БД мигрирует на актуальную
   версию автоматически (данные пациентов не изменяются, старые сессии
   завершаются).
3. Создайте первого Разработчика: `python -m backend.cli create-developer`.
   Прежний общий пароль (`app_login`, `CLINIC_ADMIN_PASSWORD`) перестал
   быть способом входа сразу после обновления — fallback не предусмотрен.
4. Войдите Разработчиком, создайте отделения («Структура») и сотрудников
   («Сотрудники»), либо загрузите оргструктуру локальным файлом:
   `python -m backend.cli import-structure structure.json`
   (файл с реальными ФИО держите вне Git). Команда печатает для каждой новой
   учётной записи собственный временный пароль — передайте каждому лично;
   повторно он не выводится.
5. У существующих пациентов лечащий врач хранился текстом — сопоставьте
   каждого с учётной записью врача в разделе «Структура» →
   «Несопоставленные лечащие врачи». До сопоставления такие пациенты видны
   только Разработчику и глобальным read-only ролям.

## Запуск

```bash
source .venv/bin/activate
uvicorn backend.app.main:app --host 127.0.0.1 --port 8420
```

Запускается **один процесс** (без `--workers`): лимиты запросов и входа
хранятся в памяти процесса. При `WEB_CONCURRENCY`/`UVICORN_WORKERS` больше 1
или втором процессе на том же каталоге данных приложение не стартует
(блокировка `CLINIC_DATA_DIR/.clinic-app.lock`).

Приложение доступно на http://127.0.0.1:8420. По умолчанию слушает **только localhost**
и не открыто во внешнюю сеть.

**Настройки** приложение и CLI берут только из окружения процесса; файл `.env` сами не
читают. Загрузите его явно: `uvicorn ... --env-file backend/.env`, systemd
`EnvironmentFile=` или `set -a; . backend/.env; set +a`. Если `backend/.env` (или `.env`
в корне) задаёт значение, которого процесс не получил, сервер не стартует, а CLI завершается
с кодом 2 — с именами расхождений, без значений. Адрес и порт прослушивания задают
`--host`/`--port` uvicorn (`CLINIC_HOST` — доверенный Host, должен совпадать с `--host`).

**Схема базы при запуске не обновляется.** Если база старше сборки, сервер останавливается
без изменений файла; обновление — только явной командой после резервной копии:
остановить сервис → `backup` → `backup-verify` → `migrate-db --confirm-offline` →
`check-db` → запуск (подробно — `OPERATIONS.md`, «Database Operations: Safe Order»).

При первом входе, если в браузере остались данные пациентов из старой localStorage-версии,
приложение предложит перенести их на сервер (однократно, только по явному подтверждению).

## Команды обслуживания

```bash
python -m backend.cli create-developer    # создать учётную запись Разработчика (bootstrap)
python -m backend.cli import-structure f  # локальный импорт оргструктуры из JSON (файл вне Git)
python -m backend.cli check-db            # только чтение: integrity_check, FK, версия схемы, таблицы; базу не меняет
python -m backend.cli migrate-db --confirm-offline  # обновить схему: проверенная копия → миграция → check-db (приложение остановлено)
python -m backend.cli consilium-schedule-check  # только чтение: счётчики нестандартных дат и записей вне сетки консилиума
python -m backend.cli backup-keygen f --key-id ID  # protected key file; key_id сохраняется в файле
python -m backend.cli backup              # encrypted backup через SQLite backup API + AES-GCM
python -m backend.cli backup-inspect f    # безопасные metadata encrypted backup без расшифровки
python -m backend.cli backup-verify f     # AEAD, integrity_check, FK и schema проверки
python -m backend.cli restore <file> --confirm-offline  # restore только при остановленном приложении (иначе отказ)
python -m backend.cli restore <file> --confirm-offline --replace-damaged  # аварийно: повреждённая база уходит в quarantine/
python -m backend.cli audit-tail          # последние события аудита
python -m backend.cli audit-prune         # удалить события старше срока хранения
python -m backend.cli purge-sessions      # удалить истёкшие сессии
python -m backend.cli notifications-generate          # сформировать due-напоминания
python -m backend.cli notifications-run-once          # обработать одну due-запись mock provider
python -m backend.cli notifications-drain --limit 100 # обработать пачку due-записей
```

## ИИ-помощник V1

Помощник работает как единый conversational assistant: пользователь не выбирает
режимы, а пишет естественным языком. Обычные безопасные вопросы обрабатываются
как general chat, навигационные вопросы отвечаются по встроенной справке о
продукте, а вопросы про пациентов, маршруты, внимание, просрочки, качество
данных и аналитику получают данные только через read-only backend tools с
серверным RBAC scope. Для очевидных операционных вопросов есть deterministic
fallback на случай недоступности локальной модели.

В локальном development-режиме backend автоматически проверяет LM Studio на
`http://127.0.0.1:1234/v1` и модель `qwen3-8b`. Если локальный AI-сервис не
запущен или модель недоступна, приложение работает штатно, а интерфейс
показывает компактное состояние «ИИ-помощник временно недоступен» без активного
поля отправки.

Для production/internal deployment используйте явную конфигурацию:
`CLINIC_ENV=production`, `CLINIC_AI_MODE=configured`, `CLINIC_AI_BASE_URL` и
`CLINIC_AI_MODEL`, либо `CLINIC_AI_MODE=disabled`. Silent autodiscovery
localhost-provider в production не используется.

`GET /api/ai/status` безопасно перепроверяет `/models`: после запуска LM Studio
доступность можно обновить кнопкой «Проверить снова» без перезапуска backend.
API key задаётся только на backend через `CLINIC_AI_API_KEY` и не возвращается
во frontend. Помощник не имеет write-tools, не хранит историю в SQLite или
браузерных storage и не получает телефон/полис ОМС через V1 tools. Запросы на
изменение данных и patient-specific клинические решения отклоняются на backend
до передачи запроса провайдеру.

## Application Security Hardening

- Production defaults disable `/api/docs`, `/redoc` and `/openapi.json`;
  API schema is available only when `CLINIC_DEBUG=true`.
- All state-changing cookie-authenticated HTTP endpoints require a session-bound
  CSRF token. Login and import/migration preview are explicitly treated as
  non-CSRF cases because they do not mutate stored clinical data. Preview
  endpoints do not write SQLite audit rows, update sessions, create files,
  create notifications, or run the actual import/migration commit.
- Pydantic request schemas reject unknown JSON fields. Import still accepts
  explicitly documented read-only export fields needed for v3 roundtrip
  compatibility, but server-side IDs, timestamps, audit actors and assignment
  decisions remain authoritative.
- Login, analytics export, import/migration, data-quality, notification worker
  and staff search endpoints have bounded in-memory abuse controls. These are
  pruned on access, capped, and protected by an in-process lock. Login bucket
  subjects hash normalized usernames. The client address comes from uvicorn,
  which trusts `X-Forwarded-For` from `127.0.0.1` by default, so the reverse
  proxy must overwrite that header (see PILOT_RUNBOOK.md). These
  controls are not a replacement for reverse-proxy or persistent rate limiting
  in a multi-process production deployment.

## Данные, защита каталога и резервное копирование

- **База**: `backend/data/clinic.db` (SQLite schema v19, исключена из Git и не раздаётся по HTTP).
  v7 добавила legacy patient-level поля `consilium_code`, `pgi_code` и таблицу
  `patient_diagnosis_history`; v8 добавляет структурированное решение ОК на
  событии маршрута и структурированный результат ПГИ; v9 добавляет дату
  результата ПГИ и выводит `disease_stage`/`future_plans` из active contract;
  v10 добавляет персональные записи на онкологический консилиум; v11 — роль
  председателя, статусы, возврат на доработку, подписание и назначения лечения.
  v12 добавляет полис в записи, избранное председателя, хирургический и
  химиотерапевтический реестры и Excel-экспорт; v13–v17 — локализация и код
  схемы, ГОК, архив врача, сетка председателя и уведомление о доработке,
  ограничения «один слот — одна запись» и «одна запись на пациента»; v18 —
  отметка повторной отправки после доработки и неизменность подписанных
  решений (триггер БД), раунды доработки и лечащий врач на момент подписи.
  Восстанавливаются зашифрованные копии только проверенных сборок
  (v0.9.0-stable v9, Max v17, текущая v18) — по точной структуре схемы, с
  миграцией временной копии (см. BACKUP_SECURITY.md). Импорт `replace`/`update`
  и удаление карточки не выполняются, если затронули бы записи консилиума.
- **Сохранность медицинской истории (схема v28, WP-C)**: карточка с медицинской
  информацией (диагноз, жалобы, ПГИ и др.) или историей физически не удаляется
  (409 `PATIENT_HAS_CLINICAL_HISTORY`); правки
  карточки, согласий, вопросов внимания, сотрудников и выдача файлов с ПДн
  сохраняются только вместе с записью аудита (503 без неё); исправления фактов
  событий хранятся в истории, факт в будущем отклоняется (историческая выгрузка
  принимается с предупреждением и аудитом, факт помечается неподтверждённым); правка карточки и
  чек-листа проверяет версию (409 при устаревших данных); журнал аудита и
  история защищены триггерами, `check-db` сверяет их определения. Подробно —
  `OPERATIONS.md`, раздел «Схема v28».
- **Демо-данные**: `backend/scripts/seed_consilium_demo.py` и
  `seed_test_patients.py` работают только при `CLINIC_ENV=demo` и файле
  `.clinic-demo` в `CLINIC_DATA_DIR`; перед сбросом консилиума создаётся
  зашифрованная резервная копия.
  История диагноза хранит
  patient id, timestamp, actor user id и старый/новый диагноз для отображения в
  timeline; audit пишет только техническое событие `patient_diagnosis_changed`
  без значений диагноза. Поля `consilium_code`/`pgi_code` сохранены как
  deprecated compatibility fields для импорта/экспорта v7 и не используются
  новой UI-моделью.
- Локальный словарь МКБ-10 включает D37–D48 и текущие D00–D09. In situ D00–D09
  автоматически предлагают уже существующий профиль клиентского пути только
  там, где локализация однозначно соответствует профилю; остальные коды
  остаются без автоподстановки, чтобы не создавать фиктивные профили.
- Статус «Клиентский путь определён» в форме зависит от выбранной локализации:
  если в группе локализации есть хотя бы один уже настроенный профиль, сроки
  доступны. Конкретный внутренний `nosology` по-прежнему подставляется только
  по выбранному диагнозу, когда соответствие однозначно.
- Пороговые сроки цветовой легенды подтверждены врачебной обратной связью.
- **Encrypted backups**: создайте key file и настройте `CLINIC_BACKUP_KEY_FILE`, затем
  `python -m backend.cli backup` → `backend/data/backups/clinic_<дата>.cbk`.
  Копия делается через SQLite backup API, проверяется и упаковывается в Clinic Backup Format v1
  с AES-256-GCM. Существующий backup не перезаписывается: выберите новое имя файла.
- **Проверка копии**:
  ```bash
  python -m backend.cli backup-inspect backend/data/backups/clinic_20260730_120000.cbk
  python -m backend.cli backup-verify backend/data/backups/clinic_20260730_120000.cbk
  ```
  `inspect` показывает только безопасный header; `verify` расшифровывает во временную директорию,
  проверяет AEAD, SQLite integrity, FK и версию схемы.
- **Защита каталога**: держите `backend/data/` доступным только владельцу. На macOS/Linux:
  `chmod 700 backend/data` (файлы копий приложение само выставляет в `600`). На Windows
  `chmod` не действует — ограничьте доступ через свойства папки (NTFS ACL).
- **Шифрование рабочей БД на диске обязательно.** Encrypted backup не шифрует live-файл
  `clinic.db`, WAL/SHM, swap, crash dumps и filesystem snapshots. Для production требуется
  полное шифрование диска/тома: FileVault (macOS), BitLocker (Windows), LUKS (Linux), плюс
  ограниченные OS permissions. SQLCipher и application-level DB encryption остаются отдельным
  архитектурным решением.
- **Ключи**: ключ backup не хранится в Git, `.env.example`, shell history, рядом с DB или рядом
  с backup. Создайте его через `python -m backend.cli backup-keygen /secure/offline/location/clinic-backup.key`,
  храните отдельно и
  резервируйте по операторской процедуре. Потеря ключа делает соответствующие backups
  невосстановимыми. Подробно: `BACKUP_SECURITY.md` и `OPERATIONS.md`.
- **Восстановление данных**:
  ```bash
  python -m backend.cli restore backend/data/backups/clinic_20260730_120000.cbk --confirm-offline
  ```
  До restore остановите приложение и notification worker: пока работает сервер, CLI-команда
  с базой или другой restore, команда отказывает до любых изменений (межпроцессные блокировки
  `CLINIC_DATA_DIR/.clinic-app.lock` и `.clinic-db.lock`). Команда проверит формат, key_id,
  AEAD tag, SQLite integrity, FK и ожидаемую версию схемы, сделает и проверит encrypted
  recovery copy текущей базы, спросит подтверждение и заменит базу атомарно. Повреждённую
  текущую базу заменяет только с `--replace-damaged`, перемещая её файлы в `quarantine/`
  (не удаляя).
  Повреждённая, изменённая, усечённая, plaintext или несовместимая копия отклоняется, текущая
  база при этом не меняется. После restore обязательно выполните `python -m backend.cli check-db`;
  только затем запускайте приложение снова. После восстановления все прежние сессии
  недействительны — войдите заново.
- **Журнал аудита** хранится в той же базе (таблица `audit_events`), содержит только
  обезличенные события (без ФИО, диагнозов, паролей и токенов). Срок хранения — 365 дней,
  очистка вручную: `python -m backend.cli audit-prune`.

## Терминология: локализация и поле `nosology`

- В интерфейсе врач выбирает **локализацию** и релевантный диагноз.
- Наличие клиентского пути в форме определяется сразу по локализации: если для
  неё есть хотя бы один настроенный профиль, сроки доступны до выбора диагноза.
  Если пути нет, сроки для такой локализации не рассчитываются.
- Конкретный внутренний профиль для новой записи система выбирает по диагнозу
  только при однозначном соответствии; спорные коды не создают фиктивный путь.
- Во внутреннем контракте — API, схеме SQLite и JSON-формате импорта/экспорта — оно
  носит legacy-имя **`nosology`**.
- Имя `nosology` **намеренно сохранено** для обратной совместимости с существующей
  базой данных, а также с уже сделанными экспортами и импортами.
- Это не забытое старое название: переименовывать поле не нужно — без отдельной
  миграции схемы БД и формата экспорта это сломает совместимость.

## Поле полиса ОМС

- В интерфейсе поле называется **«Номер полиса ОМС»**.
- Во внутреннем контракте API и JSON-формате импорта/экспорта используется
  `policyNumber`; в SQLite — nullable-колонка `patients.policy_number`.
- Значение хранится строкой, чтобы не терялись ведущие нули. Пробелы по краям
  удаляются, визуальные пробелы и дефисы внутри номера перед сохранением
  нормализуются.
- Старые запросы и JSON-файлы без `policyNumber` остаются валидными; в UI
  пустое значение показывается как «Не указан».

## Production-развёртывание (если понадобится сетевой доступ)

Локальный HTTP-режим предназначен только для работы на одной машине. Для доступа по сети:

1. Поставьте перед приложением HTTPS reverse proxy (nginx/caddy) с TLS-терминацией.
2. Установите `CLINIC_HTTPS=true` в окружении процесса (systemd `EnvironmentFile=` или
   `--env-file`) — включит `Secure` на cookie и HSTS. Проверьте строку запуска в журнале:
   `https=True`.
3. Оставьте uvicorn слушать 127.0.0.1; наружу смотрит только proxy.
4. Выполните требования к proxy из PILOT_RUNBOOK.md («Reverse proxy
   requirements»): перезапись `X-Forwarded-For`, `X-Forwarded-Proto`,
   журнал без строки запроса, `client_max_body_size 16m`.
5. Ограничьте доступ на уровне сети (VPN/файрвол).

Подробный разбор модели безопасности и остаточных ограничений — в `SECURITY_AUDIT.md`.
Правила центра качества данных и его ограничения — в `DATA_QUALITY.md`.
