# UX-прототип для сотрудников («спокойное рабочее место»)

Дизайн-исследование на базе прототипа Stage 3.5 (`../redesign/`, commit
921cdee). Утверждённое направление: компактная таблица пациентов,
представления со счётчиками, линия маршрута, уведомления в порядке
«состояние → согласие → новое напоминание → история». Вторая итерация
вернула привычное из Stage 3.5: голубую палитру, боковую навигацию с
иконками, восемь вкладок карточки и видимые кнопки частых действий.

Не подключён к backend и API. Данные — синтетические (`../redesign/data.js`,
`nosology.js`, `icd10.js`, без изменений). Изменения живут в памяти вкладки и
пропадают при перезагрузке; SMS и сообщения не отправляются. В хранилище
браузера пишутся только `staffux-role` и `staffux-theme`.

## Запуск

Из корня этого worktree (прототип берёт шрифты из `static/fonts.css` и
данные из `prototype/redesign/`):

```bash
python3 -m http.server 8790 --bind 127.0.0.1
```

Открыть: <http://127.0.0.1:8790/prototype/staff-ux/>

Полоса «Прототип · синтетические данные» под верхней панелью — управление
демонстрацией, не часть интерфейса: роль (6 ролей), состояние экрана
(данные, загрузка, пусто, ошибка), ссылка на прежний прототип Stage 3.5.

## Доступность и клавиатура

- `/` — поиск пациента; `Esc` — закрыть окно, меню, список или панель.
- Вкладки карточки: стрелки, Home, End.
- Выпадающие фильтры (кнопка `role="combobox"` + `role="listbox"`):
  Enter / Пробел / ↓ / ↑ — открыть; ↑ ↓ Home End PageUp PageDown — выбор;
  Enter — применить; Esc — закрыть с возвратом фокуса; Tab — закрыть;
  ввод букв — переход к пункту. Выбранный пункт отмечен галочкой и
  `aria-selected`, текущий — `aria-activedescendant`.
- Tab не выходит из открытого окна; после закрытия фокус возвращается к
  кнопке, которая его открыла.
- Контраст (WCAG AA): белый на синей кнопке — 4,7 (тёмная тема) и 6,84
  (светлая); акцентный текст — от 5,9; кольцо фокуса — от 6,3 к фону.

## Кнопки

Одна система для всех экранов (`styles.css`, блок «Кнопки: единая система»):

| Вид | Класс | Когда |
| --- | --- | --- |
| Основное действие | `.btn--primary` | одно главное действие экрана, формы или диалога |
| Второстепенное | `.btn` | остальные действия, с обводкой |
| Опасное | `.btn--danger` | действие с необратимыми или важными последствиями: красный текст и тонкая красная обводка; всегда открывает подтверждение |
| Подтверждение опасного | `.btn--danger-solid` | только кнопка окончательного подтверждения в диалоге (диалоги с `kind: 'danger'`) |
| Вспомогательное | `.btn--text` | ссылки-действия без рамки («Изменить» в разделе, «Обновить», «Сбросить») |
| Иконка | `.btn--icon` | действие-иконка с подписью для экранного диктора |
| Удаление слота | `.slot__del` | малое опасное действие-иконка в карточке слота: 32 × 32 px (на телефоне 40 × 40), нейтральная рамка, красная иконка, красная рамка и фон при наведении; место под кнопку зарезервировано, время и состояние не перекрываются |

Размеры: обычный (40 px) — шапка страницы, формы, панель подробностей, диалоги;
`.btn--sm` (32 px) — действия внутри разделов, строк и списков; в одном ряду —
кнопки одного размера. На экранах до 767 px — 44 и 40 px. Скругление у всех —
`--r-md` (8 px), фокус — обводка 2 px цветом `--focus` без изменения формы.
В названиях действий нет троеточий; подтверждение показывает диалог.

## Аналитика: что считается и как

- **Текущее состояние** (на момент расчёта, период не влияет): всего, активные,
  требуют внимания, с просрочками, проблемы качества данных; этапы, состояние
  маршрутов, локализации, причины внимания, нагрузка врачей, качество данных.
- **За период**: динамика новых пациентов и завершений (с таблицей данных),
  просрочки с плановой датой в периоде.
- Правила — как в Stage 3.5 (`analytics/service.py`, `data_quality.py`), расчёт
  в браузере по синтетическим данным в области доступа роли.
- Заполненность обязательных полей — **правило прототипа**: доля заполненных
  полей «ФИО, телефон, полис ОМС, диагноз, текущий этап, лечащий врач». В
  приложении эта сводка в аналитику не передаётся, поэтому прежний показатель
  «100%» Stage 3.5 (заглушка) не перенесён.
- Период длиннее 90 дней: итоги периода и CSV («Скачать сводку CSV») считаются
  за весь период, график показывает последние 90 дней — об этом есть подпись.
- «С открытой отметкой «Требует внимания»» — только пациенты с незакрытой ручной
  отметкой; просрочки без отметки — в «С просроченными событиями».
- Каждый интерактивный показатель открывает список с тем же числом записей
  (для чек-листов — по одному незавершённому пункту на строку).
- Загрузка расписания председателя — **демонстрационная оценка**: условные
  16 слотов на группу в день, а не реальная вместимость.
- Отличия от Stage 3.5: детализация «С просроченными событиями» — пациенты с
  текущими просрочками без фильтра периода (просрочки периода — отдельный
  показатель); нагрузка врачей отсортирована по убыванию.

## Решение ОК и перевод этапа

Утверждено владельцем проекта: ручное решение ОК и перевод этапа — две
самостоятельные операции. Сохранение решения не переводит пациента, перевод
не создаёт и не меняет решение, ручное решение и подписанное решение
председателя — разные сущности.

**Совместимость с API.** Текущий backend сохраняет ручное решение только через
`change_stage` — вместе с переводом этапа. Отдельная серверная операция ещё не
реализована, её разработка относится к WP2.2. **Прототип в этом сценарии с
текущим API не совместим** — он показывает целевое поведение на синтетических
данных.

«Отметить решение ОК…» (`core.js`: `decisionAvailability`, `applyManualDecision`):
- только на этапе «Направлен на ОК» и только при праве редактировать этого
  пациента (врач, заведующий, председатель, разработчик — в своей области
  доступа; заместитель и ЦАОП — нет);
- привязана к конкретному событию этапа ОК; при нескольких событиях событие
  выбирается явно, последнее событие автоматически не выбирается; решение
  тоже выбирается явно (значения по умолчанию нет);
- меняет только выбранное событие (поле решения и признак ручной отметки с
  временем и автором), этап не меняет, записи консилиума не трогает;
- **без повторной записи**: если в событии отметка уже есть, оно показывается с
  этой отметкой (решение, автор, время) и недоступно для выбора; если отмечены
  все события этапа, диалог только показывает существующие отметки. Изменение
  уже сохранённого решения — отдельная процедура, не согласована (WP2.2);
- показывается отдельно от подписанного решения председателя.

«Перевести на этап…» (`applyStageChange`):
- самостоятельный диалог, новый этап выбирается явно (значения по умолчанию нет);
- факт перевода записывается в последнее событие текущего этапа, как в
  `change_stage`, **только если факта ещё нет**; поля решения ОК не создаются
  и не меняются;
- если у последнего события факт уже записан, диалог подставляет его и
  предупреждает; другая дата или любое непустое время, отличное от записанного
  (в том числе если записанное время пустое), блокируют перевод с объяснением
  (`stageChangeConflict`), данные не меняются. Пустое поле «Время» означает,
  что изменение времени не запрошено. Совпадающий факт остаётся как есть. Новой процедуры исправления истории нет — факт события по-прежнему
  правится обычным редактированием события на вкладке «События и даты»;
- «Дополнительное обследование» и «Диагноз не подтверждён» (меню «Ещё
  действия») сохраняют существующий факт, а если его нет — ставят сегодняшнюю
  дату, как раньше;
- отличие от текущего backend: `change_stage` перезаписывает факт последнего
  события без проверки; блокировка — поведение прототипа, для API это вопрос
  WP2.2.

Блок «Онкологический консилиум» в «Обзоре» (`consiliumSummary`):
- «Подписанные решения председателя» — только записи со статусом «Решение
  подписано» (включая архивные), сколько бы их ни было;
- «Текущая запись на консилиум» — статус последней записи отдельной строкой;
  неподписанная запись не подменяет подписанное решение;
- «Ручная отметка решения ОК» — из событий маршрута;
- решения не синхронизируются друг с другом, этап пациента не меняется.

**Существующие ограничения** (новых медицинских правил прототип не вводит):
- backend (`change_stage`): решение ОК допустимо только с этапа «Направлен на
  ОК»; решение «Диспансерное наблюдение» — только при переводе на этап
  «Диспансерное наблюдение»; решения «Определение / Изменение тактики
  лечения» — только при переводе на «Направлен на лечение» или «Проходит
  лечение». Эти проверки относятся к совмещённой операции; как они будут
  применяться к раздельным операциям — решается в WP2.2, поэтому прототип
  не связывает выбранное решение с выбранным этапом;
- backend: допустимые значения решения — три кода `consilium_decision`;
  перевод возможен только на другой этап;
- варианты перевода с этапа «Направлен на ОК» в прототипе — как в карточке
  Stage 3.5: «Направлен на лечение», «На обследовании», «Диспансерное
  наблюдение», «Диагноз не подтверждён» (backend сам набор переходов не
  ограничивает);
- подписанное решение ставит только председатель в разделе консилиума
  (Stage 3.5); подписание этап пациента не меняет.

## Ближайшее событие

Ближайшее событие — самое раннее открытое (без факта) событие по дате и
времени (`core.js`, `pickNextEvent`): просроченные — из всех этапов маршрута
(как правило просрочек качества данных), предстоящие и без даты — из текущего
этапа. Поэтому просрочка не скрывается более поздним событием, а «Рабочий
день», список пациентов, карточка, помощник и аналитика считают просрочки
одинаково. Правил приоритизации нет — только хронология.

### Аудит источников

- **Основное приложение (`clinic_tracker_new`, a3fbe00)**: модуля консилиума
  нет — ни маршрутов, ни таблиц, ни прав `*Consilium`. Есть только поле события
  `consiliumDecision` (ручная отметка решения ОК при переводе этапа).
- **WP2.1 (`clinic_tracker_wp21`, 19a22b4)**: полный модуль — `routes/consilium.py`,
  `services/consilium.py`, таблицы записей, слотов, истории возвратов, избранного;
  аудит; ~2 200 строк интерфейса. Прототип повторяет именно его.
- **Stage 3.5 (`prototype/redesign/`)**: интерактивная копия интерфейса WP2.1 —
  сетка по группам, форма записи, модальное окно решения, архив, реестры,
  аналитика председателя.

Факты контракта (WP2.1), на которых построен прототип:
- статусы: хранятся `recorded / in_review / signed`; публично — «Записан»,
  «На рассмотрении», «На доработке», «Возвращён с доработки», «Решение
  подписано» (в WP2.1 — «Подписан»). Новых состояний нет; «статус
  рассмотрения» и «статус решения» в системе — одно поле;
- запись создают роли с `bookConsilium` (врач, заведующий, разработчик);
  рассматривает, подписывает и возвращает только председатель
  (`decideConsilium`); слоты в интерфейсе — только председатель;
- одна запись на слот (дата + время + группа), одна действующая запись на
  пациента; группа определяется кодом МКБ-10 карточки;
- текущая неделя открыта автоматически (09:00–16:45, шаг 15 минут, все дни);
  следующие — слотами председателя (интервал только 15/30/60 минут, не длиннее
  12 ч). Как `generate_schedule()` (INSERT OR IGNORE): уже открытый день можно
  расширять, повторы пропускаются, существующие слоты и записи не меняются;
  сохранённый слот замещает автоматический с теми же датой и временем — так
  председатель явно открывает выходной текущей недели. Запрет прошедших дат —
  правило интерфейса (сервер его не проверяет). Аудит открытия пишется и при
  `created=0`; в журнале прототипа такая запись помечена «без изменений»;
- удаление слота (`delete_schedule_slot()`) удаляет только сохранённую строку;
  на текущей неделе `schedule_slots()` снова подставляет автоматический слот на
  то же время, поэтому удаление **не закрывает** время. Прототип показывает это
  предупреждением до удаления и точным сообщением после; занятый слот и слоты
  автоматической недели удалить нельзя;
- изменять, переносить и удалять запись может только автор и только до начала
  рассмотрения; правка записи «На доработке» = повторная отправка;
- возврат — с обязательным комментарием, отличным от предыдущего; раунды
  хранятся навсегда; подпись снимает текущий комментарий, история остаётся;
- подписанное решение неизменяемо (триггер); можно только архивировать (автор)
  и отметить направление на хирургию (председатель);
- подпись сохраняет снимок этапа маршрута, но **этап не меняет** и события
  пациента не трогает;
- архив — отметка автора на своей подписанной записи; председатель видит все
  записи, включая архивные; удаление с историей возвратов — мягкое.

### Решения по компоновке

**Расписание.** Рассмотрены три варианта:
- *недельная сетка (дни × время)*: 7 × 32 ячейки × 8 групп — на телефоне
  нечитаема, требует горизонтальной прокрутки;
- *список дней с раскрываемыми слотами*: удобно на телефоне, но врачу нужно
  сравнивать дни между собой, а раскрытые списки уезжают вниз;
- *полоса недели + слоты выбранного дня* — выбран. Сценарий врача «найти
  ближайший свободный слот»: в полосе сразу видно число свободных слотов по
  дням; один клик — слоты дня. Сценарий председателя «проверить загрузку и
  открыть день»: в полосе видны неоткрытые дни, форма открытия — под днём.
  Одна группа за раз: запись всё равно возможна только в группу по МКБ-10.

**Рабочее место председателя.** Модальное окно Stage 3.5 закрывало список и
не позволяло переходить между пациентами. Выбрана схема «список заседания
слева, подробности справа»: показатели над списком работают как фильтры,
в подробностях — сведения, «Что дальше», форма решения и история, кнопки
«‹ ›» для перехода к соседнему пациенту. На экранах до 1023 px — список и
подробности по очереди с кнопкой «К списку».

**Подписание и возврат.** Обычные действия (начать рассмотрение, выбрать
слот) — без подтверждения; подписание (необратимо) и удаление записи — с
подтверждением, фокус на «Отмена». Возврат требует причину.

### Что потребуется от WP2.2 и WP2.3

- **WP2.3**: закрытие отдельных времён автоматической недели (сейчас удаление
  сохранённого слота возвращает автоматический); серверный запрет записи на прошедшее время; выходные — только
  явно открытые; пустая таблица слотов не разрешает произвольное время;
  оформление задним числом председателем с отдельной причиной и аудитом.
  В прототипе первые три показаны как UX-состояния (переключатель «Показывать
  целевые правила WP2.3» в «Правилах записи»), четвёртое не реализовано.
- **WP2.2**: отдельная серверная операция ручной отметки решения ОК (сейчас
  только через `change_stage`). Подписанное решение консилиума с ней не
  связано и этап не меняет — так уже в WP2.1.
- **Перенос в основное приложение**: модуль консилиума есть только в ветке
  WP2.1; в основной ветке (a3fbe00) его нет.
