# Прототип редизайна «Системы планирования»

Визуальная демоверсия для согласования. Не подключена к backend и API,
работает только на синтетических данных (`data.js`); изменения живут в
памяти вкладки и пропадают при перезагрузке. Основной интерфейс
(`index.html`, `static/`) не изменён.

## Запуск

Из корня репозитория (прототип берёт шрифты из `static/fonts.css`):

```bash
python3 -m http.server 8765 --bind 127.0.0.1
```

Открыть: <http://127.0.0.1:8765/prototype/redesign/>

## Что внутри

- Переключатель «Роль» в верхней панели — шесть ролей приложения (см. ниже).
- Переключатель «Состояние»: данные, загрузка, пусто, ошибка.
- Кнопка с луной — светлая и тёмная тема (по умолчанию — системная).
- Клавиша `/` — фокус на поиске, `Esc` — закрыть верхнее окно (окно →
  лист фильтров → уведомления → помощник).
- «ИИ-помощник» в верхней панели и «Спросить помощника» в карточке
  пациента. Это демонстрация: модель не подключена, ответы заготовлены по
  синтетическим данным в области доступа выбранной роли и помечены
  «Демо-ответ». Состояние «Ошибка» показывает недоступность помощника.
- «Сообщения» — переписка врача с пациентами по сценарию Patient Portal
  v0.5.1. Только у роли «Врач» и только по своим пациентам. Демонстрация:
  сообщения живут в этой вкладке, не доставляются пациенту, не хранятся на
  сервере и не синхронизируются с мобильным приложением.
- **Вход и смена временного пароля** («Выйти» внизу боковой панели).
  Только визуальная имитация: ничего не проверяется и не хранится, поля
  пароля очищаются после каждой попытки, в хранилище браузера остаются
  только `proto-role` и `proto-theme`. Исход выбирается в блоке
  «Демонстрация»: успешный вход, временный пароль, неверный пароль (401),
  слишком много попыток (429), вход под ролью только для просмотра. Тексты
  ошибок взяты из приложения; «Введите логин и пароль.» и «Заполните все
  поля.» — тексты прототипа.
- **Уведомления** (колокольчик). Сформированы прототипом по синтетическим
  данным в области доступа роли, сервер не опрашивается. Типы и заголовки —
  как во внутренних уведомлениях приложения (просрочено, на сегодня, скоро
  срок, чек-лист, требует внимания, консилиум возвращён на доработку —
  только автору записи); порядок — непрочитанные, затем по дате события.
  Вкладки «Все / Новые / Просрочено / Сегодня», «Прочитано», «Прочитать
  все», переход к пациенту или к записи консилиума, пустое состояние.
  Это напоминания сотруднику, а не сообщения пациентам.
- **Компоненты прототипа** (`#/kit`, ссылка внизу боковой панели):
  вкладки (стрелки, Home/End), подтверждение опасного действия, мобильный
  лист фильтров, выбор даты и времени с проверками, поиск по МКБ-10
  (код, латинская или кириллическая «С», слова названия, фильтр по
  локализации, выбор с клавиатуры). Справочник `icd10.js` перенесён без
  изменений из `static/app.js` (`icd10Localizations`).

## Роли

Источник прав — `backend/app/policy.py` (`permissions_payload`,
`resolve_create_doctor`) и `backend/app/db.py` (стратегии области
доступа); видимость разделов — `navVisibility` в `static/app.js`.
Прототип повторяет эти флаги (`PERMS` в `app.js`) и не объединяет роли.

| Роль | Область | Что может |
| --- | --- | --- |
| Разработчик | все пациенты | всё, кроме решения консилиума, отметки направления и избранного председателя; единственный, кому доступны импорт с обновлением и заменой, сотрудники, структура, аудит |
| Заместитель главного врача по онкологии | все, только просмотр | просмотр и неразобранные записи |
| Заведующий ЦАОП | все, только просмотр | то же, что заместитель (в приложении права совпадают) |
| Заведующий отделением | своё отделение | пациенты, импорт (добавление), экспорт, уведомления, запись на консилиум |
| Врач | свои пациенты | то же, что заведующий, в своей области |
| Председатель консилиума | свои пациенты | пациенты, уведомления, ведение консилиума, решение, направление, избранное; без записи на консилиум, импорта и экспорта |

Лечащий врач: создавая пациента, врач и председатель становятся его
лечащим врачом (`resolve_create_doctor`), заведующий выбирает врача
отделения, разработчик — любого активного врача или оставляет без врача.

Разделы сверх приложения — «Сегодня» и «Сообщения» у врача, «Отделение»
у заведующего — это предложения редизайна. Прямая ссылка на недоступный
раздел показывает «Раздел недоступен для вашей роли».

## Расхождения (не согласованы)

Ниже — места, где серверные права и действующий интерфейс расходятся или
поведение не определено. Backend не меняется; прототип повторяет
действующий интерфейс, и это **не** продуктовое решение.

1. **Разработчик и ведение консилиума.** Сервер даёт разработчику
   `manageConsilium` (сетка, реестры, аналитика), интерфейс показывает эти
   функции только при `consiliumChair`. На странице консилиума у
   разработчика выводится пометка.
2. **Режим импорта.** Список «Добавить / Обновить / Заменить» в окне
   импорта не фильтруется по роли; режимы обновления и замены сервер
   разрешает только разработчику (иначе 403).
3. **Колокольчик у председателя.** Сводку уведомлений сервер отдаёт любому
   активному пользователю в его области, колокольчик виден, а раздел
   «Уведомления» председателю скрыт. С этапа 1 у председателя в демо-данных
   есть один свой пациент (созданный им), поэтому колокольчик у него
   показывает напоминания по этому пациенту. Ссылку «Все
   уведомления» прототип председателю не показывает, чтобы она не вела в
   недоступный раздел; как это сделано в приложении, не проверялось.
4. **Председатель как лечащий врач и переписка.** Председатель становится
   лечащим врачом созданных им пациентов, но по принятому решению
   переписка есть только у роли «Врач». Нужно ли открыть её председателю
   по своим пациентам — открытый вопрос.
5. **Переход с этапа консультации без решения ОК.** Шаг «Следующий» на
   ленте маршрута (`static/app.js`, `advanceToStage` без
   `consiliumDecision`) переводит пациента дальше без решения консилиума;
   сервер решение не требует. Намеренно ли это — не подтверждено.

Не смоделировано в прототипе: XLSX-реестр хирургических вмешательств
(в приложении его нет), уведомления о качестве данных (`data_quality`).

### Найдено на этапе 1 (карточка пациента, не согласовано)

Поведение действующей карточки, которое прототип повторяет или от
которого отходит. Backend и основной интерфейс не менялись.

6. **Маршрут скрыт у ролей просмотра.** `applyReadOnlyToPatientView`
   скрывает все кнопки панели карточки, а шаги маршрута — кнопки, поэтому
   у заместителя главного врача и заведующего ЦАОП маршрут во вкладках
   «Обзор» и «События и даты» не виден. Прототип показывает маршрут без
   действий. Это отход от приложения, его нужно подтвердить.
7. **Удаление события без подтверждения.** Кнопка с корзиной в «События и
   даты» удаляет событие сразу. Прототип повторяет это; нужно ли
   подтверждение — открытый вопрос.
8. **Переход на любой будущий этап.** Шаг «Запланирован» открывает кнопку
   «Перевести пациента на этот этап», то есть можно перепрыгнуть
   несколько этапов. Сервер переходы не проверяет (кроме правил решения
   ОК). Прототип повторяет; медицинских правил не добавляет.
9. **Решение ОК фиксирует любой, кто может править пациента.** Кнопки
   решения на этапе «Направлен на ОК» проверяют `editPatients`, а не
   `decideConsilium`, и не связаны с подписанным решением в разделе
   «Консилиум». Прототип повторяет логику и явно помечает такую отметку
   (у кнопок, в подтверждении и в карточке события) как демонстрацию, а не
   подписанное решение консилиума.
10. **Текст ошибки сервера на английском.** Пустое ФИО даёт «Не удалось
    сохранить: name must not be empty». Прототип показывает так же.
11. **Одинаковые названия шаблонов SMS.** Шаблоны `appointment_reminder` и
    `examination_reminder` оба называются «Напоминание о посещении», в
    списке «Шаблон» это две одинаковые строки. Прототип повторяет.
12. **Блок «Онкологический консилиум» в карточке** — предложение
    редизайна: в действующей карточке его нет. В прототипе помечен
    «Предложение».

## Принятые решения

### Доступ к переписке с пациентами (14.10.2026)

Заведующий отделением **не получает** автоматического доступа к содержанию
сообщений врачей с пациентами. Сохраняется текущая модель:

- переписка доступна только лечащему врачу и только в пределах его
  разрешённой области доступа;
- остальные роли (заведующий отделением, председатель консилиума,
  заместитель главного врача, заведующий ЦАОП, разработчик) не получают
  доступа к сообщениям ни через раздел «Сообщения», ни по прямой ссылке на
  диалог, ни через карточку пациента или другие разделы;
- новых прав под переписку не вводится.

Прототип уже следует этому решению: пункта «Сообщения» у этих ролей нет,
прямые ссылки показывают «Раздел недоступен», кнопки переписки в карточке
нет, текст сообщений на их страницах не выводится. Изменение модели —
только отдельным решением (см. расхождение 4).

## Файлы и CSP

`index.html` (каркас), `styles.css` (токены и компоненты), `app.js`
(экраны, роли, окна, общие компоненты), `data.js` (синтетические данные),
`icd10.js` (справочник МКБ-10), `nosology.js` (справочник клиентских
путей: сроки этапов и чек-листы), `theme-init.js` (тема до первой
отрисовки). `icd10.js` и `nosology.js` извлечены из `static/app.js` без
изменений.

В `index.html` нет встроенных скриптов и атрибутов `style`. В шаблонах
`app.js` остаются 18 атрибутов `style`, существовавших до этапа 0 (было
28; старая карточка пациента переписана без них); новых не добавлено. Их вынос в классы — до переноса в приложение с CSP
`style-src-attr 'none'`.
