# Центр качества данных

Центр качества данных помогает найти неполные, противоречивые или требующие
ручной проверки регистрационные данные пациентов до использования этих данных
в уведомлениях, аналитике и дополнительных сценариях. Раздел не является
медицинской рекомендацией и не оценивает состояние пациента.

## Архитектура

- Правила выполняются на backend в `backend/app/services/data_quality.py`.
- API находится в `backend/app/routes/data_quality.py`.
- Findings не сохраняются в отдельной таблице: они вычисляются из текущих
  данных при каждом запросе. После ручного исправления карточки проблема
  исчезает при следующем чтении.
- Схема SQLite v2 не меняется; внутреннее поле `nosology` сохранено.
- Frontend только отображает результат backend и ведёт пользователя в
  существующую карточку пациента. Отдельных write-endpoints для автоисправления
  нет.

## API

- `GET /api/data-quality/summary` — агрегаты только по текущему patient scope.
- `GET /api/data-quality/issues` — список проблем, пациенты и группы дублей с
  фильтрами `severity`, `category`, `code`, `patient_id`, `treating_doctor`,
  `department`, `search`, `sort`, `limit`, `offset`.
- `GET /api/data-quality/patients/{patient_id}` — полнота карточки, проблемы
  конкретного пациента и группы возможных дублей внутри scope.

Все endpoints требуют активную серверную сессию и используют
`policy.patient_scope_filter`. Прямой запрос к недоступному пациенту возвращает
тот же безопасный 404, что и карточка пациента. Query-параметры не расширяют
scope и не раскрывают существование чужих пациентов.

## Severity

- `critical` — данные мешают корректно построить карточку или маршрут:
  отсутствует ФИО, диагноз, текущий этап; фактическая дата в будущем;
  текущий этап противоречит истории.
- `warning` — данные требуют уточнения, но карточка может существовать:
  нет телефона, Профиля клиентского пути или лечащего врача; телефон выглядит
  некорректно; событие или план просрочены; обязательный чек-лист не завершён.
- `info` — нейтральная подсказка для ручной проверки: возможные дубли.

Severity в интерфейсе продублирована текстом, а не только цветом.

## Правила MVP

Стабильные коды:

- `missing_treating_doctor` — `treating_doctor_user_id` пуст; используется
  существующий unresolved workflow, новый механизм сопоставления не создаётся.
- `missing_required_field` — не заполнены ФИО или телефон.
- `missing_client_path_profile` — не заполнен Профиль клиентского пути
  (`nosology`).
- `missing_diagnosis` — не указан диагноз.
- `missing_stage` — не указан текущий этап.
- `invalid_phone` — заполненный телефон содержит буквы или после безопасной
  нормализации не даёт 10-15 цифр. Пробелы, скобки и дефисы допустимы.
- `actual_date_in_future` — фактическая дата некорректна или находится позже
  текущего дня.
- `planned_date_in_past` — будущий план в прошлом или плановая дата явно
  некорректна.
- `stage_sequence_violation` — текущий этап не совпадает с последней записью
  истории, этап неизвестен, история идёт назад по маршруту или даты нарушают
  хронологию.
- `overdue_event` — плановое событие в прошлом без фактического выполнения и
  без признака «плана нет».
- `incomplete_required_checklist` — для текущего Профиля клиентского пути и
  этапа есть обязательные пункты чек-листа, которые не отмечены выполненными.
- `possible_duplicate` — внутри текущего scope есть записи с совпадающими
  детерминированными признаками.

Проверяются только поля, которые уже есть в текущей модели пациента, истории,
событий, чек-листов и будущих планов. Дата рождения в модели отсутствует,
поэтому правила по дате рождения не реализованы.

## Полнота данных

`Полнота данных` — это полнота регистрационной карточки, а не медицинская
оценка. Формула фиксирована и равномерная: 6 полей дают равные доли по 1/6.

Поля:

- ФИО;
- телефон;
- диагноз;
- Профиль клиентского пути (`nosology`);
- текущий этап;
- лечащий врач (`treating_doctor_user_id`).

Одинаковые данные всегда дают одинаковый процент. Frontend не пересчитывает
показатель самостоятельно и показывает список отсутствующих полей из ответа API.

## Возможные дубли

Группы формируются только внутри patient scope текущего пользователя. Для поиска
используются bucket/index maps, без попарного сравнения всех пациентов.

Нормализация:

- телефон: удаление нецифровых символов, российская ведущая `8` нормализуется
  в `7`;
- ФИО: trim, lower, схлопывание повторных пробелов, `ё` приводится к `е`.

Признаки MVP:

- одинаковый нормализованный телефон;
- одинаковые нормализованные ФИО и возраст;
- одинаковые нормализованные ФИО и диагноз;
- одинаковые нормализованные ФИО и Профиль клиентского пути.

Возможный дубль не означает подтверждённый дубль. Автоматического объединения,
удаления, массового исправления, fuzzy matching и AI-сопоставления нет.

## RBAC

- `developer` видит весь scope, включая unresolved, и может перейти к
  существующему сопоставлению лечащего врача.
- `deputy_chief_oncology` и `caop_head` видят весь доступный им scope только
  для чтения. Новый раздел не даёт write-прав.
- `department_head` видит только пациентов врачей своих активных отделений.
- `doctor` видит только своих пациентов.

Дубли и summary строятся только по доступным пациентам. Врач не узнаёт о похожей
чужой записи, а заведующий не видит пациентов вне своих отделений.

## Аудит и безопасность

Чтение центра качества не создаёт audit event. Исправления выполняются через
существующие endpoints карточки пациента, поэтому продолжают фиксироваться
обычные CRUD-события без ФИО, телефона, диагноза, жалоб, заметок и значений
медицинских полей.

Раздел не ослабляет CSP, не использует CDN, inline handlers, inline styles,
`innerHTML`, `eval` и не пишет медицинские данные или findings в `localStorage`.

## Ограничения

- Findings вычисляются по текущему состоянию данных и не имеют истории
  подтверждения.
- Dismiss/false-positive workflow пока отсутствует.
- Правила проверяют полноту и согласованность регистрационных данных, а не
  медицинскую корректность лечения.
- Обязательность чек-листов берётся из существующей конфигурации продукта;
  сроки пунктов чек-листа не выдумываются, если их нет в модели.
- Исправления выполняются вручную через карточку пациента.
- Автоматического объединения дублей нет.

## Дальнейшее расширение

В будущих этапах можно добавить историю подтверждения findings, ручное скрытие
ложных срабатываний, дополнительные правила после расширения модели данных и
более подробные отчёты. Эти сценарии требуют отдельного проектирования RBAC,
аудита и миграций.
