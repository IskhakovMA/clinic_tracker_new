# Система управления онкопациентами — бриф для продолжения работы

## Что это
Веб-сервис для отслеживания пациентов онкологического отделения: путь от первичного приёма до завершения лечения, с регламентными сроками по профилям клиентского пути (из внутреннего документа клиники), чек-листами обследований, кликабельным таймлайном и авто-сводкой для отчётности руководителю.

## Реализованный функционал

### Модель данных пациента
- ФИО, возраст, телефон, диагноз (МКБ-10, каскадный выбор — см. ниже)
- **Профиль клиентского пути** (внутреннее поле `nosology`, см. ниже) + **Стадия заболевания** (I-IV) — новые поля
- Приоритет: Срочно / Высокий / Обычный
- ФИО Заведующего (8 фиксированных ФИО)
- `history`: массив occurrences `{ stage, enteredAt, events: [...], note, checklist }`
 - каждое `event`: `{ date, time, treatmentType, actualDate, actualTime, matchedPlan, noPlan, setAt }`
 - `date/time` = план, `actualDate/actualTime` = факт, `matchedPlan` = совпал ли факт с планом
 - одна occurrence может содержать **несколько events** (например, несколько переносов приёма)

### Путь пациента (базовый таймлайн, 7 шагов)
1. Первичный прием — **обязателен только факт** (без плана), это старт пути
2. На обследовании — здесь чек-лист исследований по профилю клиентского пути
3. Записан на прием → автоматически переименовывается в **Прием врача**, как только проставлен факт (необязательно ждать перехода на след. этап — факт можно вписать сразу в редакторе)
4. Направлен на ОК (онкоконсилиум)
5. Направлен на лечение
6. Проходит лечение
7. Завершил лечение

Механизм переопределения базовой схемы под конкретный профиль клиентского пути **заложен архитектурно, но не использован** — в присланном документе явных случаев "приём-обследование-приём-обследование-ОК" не нашлось (там везде 2 этапа). Если для конкретного профиля клиентского пути нужна другая схема — сообщить, какая именно.

### Переход между этапами — только через клик по таймлайну
Dropdown-список этапов убран полностью. Компактная схема (7 кружков: ✓ — пройдено, номер шага (1-7) — впереди, серый цвет — впереди):
- Клик по **ближайшему следующему** (жёлтый, пульсирует) — подтверждение → переход + обязательный диалог "событие состоялось по плану?" (да → факт=план; нет → ввод факта вручную)
- Клик по **пройденному/текущему** — открывает редактор дат (план+факт+тип лечения) для этой occurrence
- Клик по **дальним будущим** (не следующим) — редактор "предварительного планирования" (необязательные заметки на будущее) + кнопка "Перевести пациента сюда сейчас" (для нелинейных переходов/пропуска этапов)

**Исправлено**: раньше после перехода на следующий этап (`advanceToStage` → `changeStage`) выделение таймлайна (`selectedTimelineNodes`) сбрасывалось, и открывался placeholder "нажмите на этап выше" — пользователю приходилось кликать по только что открытому этапу второй раз, чтобы попасть в его редактор дат. Теперь `changeStage()` сам выставляет `selectedTimelineNodes[id] = 'occ:' + (новый индекс occurrence)` сразу после успешного перехода и возвращает `true`/`false` (успех/отмена), так что редактор нового этапа открывается сразу.

### Вся карточка пациента — один разворачивающийся блок
Правая панель "Информация о пациенте" убрана, всё объединено: клик по карточке (или по ▼) разворачивает единый блок — личные данные → диагноз/профиль клиентского пути/стадия → таймлайн (с редактором дат внутри) → чек-лист (если на этапе "Обследование") → классификация → подробная хронология → сводка с кнопкой копирования → удалить.

### Регламентные сроки по профилям клиентского пути (из документа `Краткая_информация_по_КП_общее.docx`)
Данные внесены в `app.nosologyData` — 20 профилей клиентского пути (простата, молочная железа, желудок, толстая кишка, яичники, тело матки, кожа, лёгкое 1-2/3-4 ст., меланома, мочевой пузырь, голова и шея ×2 варианта, печень, поджелудочная, щитовидная ×2 варианта, шейка матки ×2 варианта, почка, верхние мочевые пути). Для каждой: `stage1Days` (до первого повторного приёма), `stage2Standard`/`stage2StageIV` (до консилиума), `checklistRequired`/`checklistOptional` (+ иногда `*Stage2` варианты).

**Коэффициент приоритета** применяется к дням: Срочно ×0.5, Высокий ×0.7, Обычный ×1.0 (`getPriorityFactor()`).

Дедлайн = факт.дата предыдущего этапа + рабочие дни (`addWorkingDays()`, пропускает выходные). Отображается:
- Мелким текстом под нужными узлами таймлайна ("до ДД.ММ.ГГГГ")
- Крупным блоком в редакторе дат этапа — жёлтый (в срок) / **красный** (нарушен)

**Допущения при переносе данных из документа** (могут требовать уточнения):
- Где в тексте было "дополнительно N дней при IV стадии" → прибавлял к стандартному сроку
- Где было "для IV стадии: N дней" без слова "дополнительно" → считал заменой стандартного срока
- Раздел "Прямая кишка" в документе — про лечение **после** консилиума (химия/лучевая/хирургия), это вне текущей задачи, не переносил
- Файл-источник лежит в `~/Downloads/Краткая_информация_по_КП_общее (1).docx`, если нужно свериться

### Чек-лист исследований (на этапе "Обследование")
Для каждого профиля клиентского пути — обязательные (отмечены `*`) и опциональные пункты, чекбоксы, счётчик "выполнено X из Y", вычеркнутый текст при отметке. Хранится в `occ.checklist = {itemName: true/false}`.

### Каскадный выбор диагноза: Локализация → Диагноз (МКБ-10)
В форме добавления пациента (`#addForm`) диагноз теперь выбирается в два шага:
1. **Локализация** (`#diagnosisLocalization`) — 16 укрупнённых анатомических групп (губа/рот/глотка, пищевод/желудок/кишечник, печень/жёлчь/поджелудочная, дыхательная система, кости, кожа, мягкие ткани/брюшина, молочная железа, женские/мужские половые органы, мочевыделительная система, глаз, нервная система, эндокринные железы, лимфоидная/кроветворная ткань, неуточнённая/множественная локализация).
2. **Диагноз** (`#diagnosis`) — изначально `disabled` с плейсхолдером "-- Сначала выберите локализацию --"; `onchange` на локализации (`app.onLocalizationChange()`) заполняет его подкодами МКБ-10 **четвёртого знака** (после точки, например `C50.2`, не просто `C50`), отфильтрованными по выбранной локализации.

Данные лежат в `app.icd10Localizations` (JS-объект, ~640 диагнозов, вставлен перед `nosologyData`) — для каждой локализации `{ label, diagnoses: [{code, label}] }`. Собраны с classinform.ru + верифицированы по официальному справочнику RUSSCO 2018 (`rosoncoweb.ru/standarts/RUSSCO/2018/2018-mkb10.pdf`).

**Исправленные ошибки в исходном (старом) списке диагнозов при сборе данных:**
- Код **C89** был в старом списке ("Миелома...") — такого кода **не существует** в МКБ-10 (классификация идёт C88 → C90 напрямую), убран.
- C90–C97 в старом списке были смещены/перепутаны (например C90 значился как "Лимфолейкоз", хотя это C91) — исправлено по официальным данным.
- C30/C31/C32 в старом списке дублировали "гортань" — теперь верно: C30 = полость носа и среднее ухо, C31 = придаточные пазухи, C32 = гортань.

**Коды без подразделения на 4-й знак** (у них в диагнозе остаётся код без точки, т.к. подкодов нет): C61 (простата), C64, C65, C66 (почка/лоханка/мочеточник), C73 (щитовидная), C97, D24 (молочная железа, доброкач.), D27 (яичник, доброкач.), D34 (щитовидная, доброкач.) и ещё несколько — полный список см. в `app.icd10Localizations`.

**Обратная совместимость**: у всех 9 демо-пациентов и вообще у пациентов, добавленных ДО этого изменения, `diagnosis` — старый краткий код без точки (например `C34`, `C50`). Это не ломается — поле `diagnosis` как хранилось строкой, так и хранится; просто новые пациенты, добавленные через форму, будут получать код с уточнением после точки. Инлайн-редактирование диагноза в развёрнутой карточке пациента (в блоке "Медицинская информация") **осталось как было** — обычное текстовое поле, каскад туда не добавлялся (эта форма не была в фокусе задачи).

**Локальный запуск для тестирования**: создан `.claude/launch.json` (`clinic-tracker` — `python3 -m http.server 8934 --directory clinic-tracker-python`), чтобы preview-браузер мог грузить файл как живую страницу (а не статический снэпшот) и выполнять JS.

### Редизайн под "спокойный современный" вид (убрали фиолетовый градиент отовсюду)
Пользователь попросил современный, спокойный дизайн, "чтобы не рябило в глазах" — посмотрел референсы (Primer/GitHub design system, современные healthcare/CRM дашборды). Главная находка: фиолетовый градиент `linear-gradient(135deg, #667eea 0%, #764ba2 100%)` был размазан по **7 разным местам** (кнопка входа, "Список пациентов" toolbar целиком, chip "N пациентов", активные фильтры, primary-кнопки, бейдж текущего этапа) плюс отдельный розовый градиент на кнопке "Выход" — это и создавало ощущение "рябит": слишком много насыщенного цвета конкурирует за внимание одновременно с уже цветными пилюлями приоритета/этапа/срока.

**Новые CSS-токены** (добавлены в `:root` / `:root[data-theme="dark"]`):
- `--accent` (`#4f46e5` светлая / `#6366f1` тёмная — приглушённый индиго, не кислотный, перекликается с фиолетовым тоном логотипа МКНЦ, но не "конфетный")
- `--accent-hover`, `--accent-soft` (полупрозрачная заливка для tint-фонов/выделения), `--accent-ring` (для кольца выделения — раньше был захардкожен как `rgba(102,126,234,0.45)`, теперь тема-зависимый токен)
- `--shadow-sm` / `--shadow-md` / `--shadow-lg` — заменили десяток разных ручных `box-shadow: 0 Npx Mpx rgba(0,0,0,0.1-0.3)` на 3 согласованных уровня элевации, значительно мягче прежних (было вплоть до `0 20px 60px rgba(0,0,0,0.3)` на логин-боксе и модалках — теперь `--shadow-lg` мягче и с бордером в довесок, а не только тяжёлой тенью)
- `--bg-page` — плоский нейтральный фон вместо трёхстопового диагонального градиента `--bg-grad-1/2/3` (диагональный градиент на фоне страницы — типичный "AI-шаблонный" приём, плюс конфликтовал по цвету с градиентными кнопками поверх)

**Что заменено на сплошной `var(--accent)` вместо градиента**: `.btn-login`, `.stat-chip-total`, `.filter-btn.active`, `.btn-primary`, `.modal-btn-primary`, бейдж текущего этапа в карточке пациента (`renderPatientDetails`). Toolbar "Список пациентов" (`.section-header`) — раньше сплошная плашка градиентом на всю ширину, теперь нейтральный `var(--surface-alt)` с нижней границей (текст/кнопки внутри стали обычной тулбар-панелью, а не "белым на фиолетовом"); кнопка "+ Добавить пациента" при этом стала solid-accent (она — главный CTA тулбара), "Экспорт"/"Импорт" остались нейтральными вторичными кнопками (не потребовали правок — уже были на `var(--surface-alt)` с бордером из прошлой сессии).

**Кнопка "Выход"** — была розово-красный градиент (`#f093fb`→`#f5576c`), теперь приглушённая красная "ghost"-пилюля (`var(--surface-alt)` фон, `#dc2626` текст, красная рамка при hover) — логаут не настолько частое/важное действие, чтобы кричать градиентом.

**Шрифт**: `'Segoe UI', Tahoma, Geneva, Verdana` (устаревший Windows-стек 2000-х) → системный стек `-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, 'Helvetica Neue', Arial` — тот же, что использует GitHub/большинство современных SaaS.

**Не трогали намеренно на тот момент**: приглушённая пастельная цветовая маркировка приоритета/этапа/срока — она уже была приведена к спокойному tint-виду в предыдущей сессии. **(Это изменилось в следующей правке, см. ниже — "Карточка пациента: статусы красятся по приоритету")**.

### Карточка пациента в списке: убрали пилюлю приоритета, статусы красятся по приоритету, фильтры без заливки
Три связанных правки за один заход, все — реакция на "слишком много независимых цветовых систем одновременно на одной карточке" (у приоритета был свой цвет, у этапа — свой, у типа лечения — свой, у срока — свой; итого 4 разных источника цвета на одной карточке).

1. **Пилюля приоритета ("СРОЧНО"/"ВЫСОКИЙ"/"ОБЫЧНЫЙ" справа от ФИО) — убрана.** Она дублировала цветную полосу слева (`.patient-card` `border-left`), это и предложил убрать пользователь. Полосу сделали заметнее взамен: было `border-left: 5px solid <непрозрачный цвет>`, стало `border-left: 9px solid <тот же цвет, но rgba с alpha 0.55>` — шире, но мягче/прозрачнее. Класс `.priority-pill` и связанный `<span>` в `renderPatients()` удалены как мёртвый код.
2. **Стадия и тип лечения на карточке теперь красятся по приоритету пациента, а не по своей собственной категории.** Раньше бейдж этапа брал цвет из `stageBadgeClass[p.stage]` → `.stage-*` (7 разных пастельных оттенков, свой цвет на каждый этап), а `treatmentBadge` был всегда фиксированного оранжевого тона. Теперь оба используют новый класс `priority-tint-${p.priority}` (`.priority-tint-urgent/high/normal` — те же rgba-тона, что раньше были у убранной `.priority-pill`, просто переиспользованы под новым именем). Смысл: цвет на карточке пациента теперь ОДИН источник правды — приоритет пациента, а не "этап + приоритет + тип лечения — три разных палитры одновременно". `stageBadgeClass` (JS-объект) удалён как мёртвый код — `.stage-*` CSS-классы остались, но теперь используются только в верхней stat-bar (там они по-прежнему обозначают этап, а не приоритет — это отдельный, глобальный контекст, не привязанный к конкретному пациенту).
3. **Исключение — индикатор срока (`.date-indicator-*`, красная пульсирующая точка) НЕ красится по приоритету, остался как есть.** Явное требование пользователя: красный должен быть зарезервирован только за предупреждениями о датах (не проставлена / близкий срок / просрочка) — это не про то, насколько пациент приоритетен, а про то, горит ли конкретный дедлайн. Если перекрасить этот индикатор по приоритету, "срочный" пациент с датой на 3 недели вперёд выглядел бы так же тревожно, как реально просроченный — что вводит в заблуждение. Поэтому `renderDateIndicator()`/`getDateIndicatorCategory()` не тронуты.
4. **Верхняя строка статистики (`.stats-bar` чипы) и все 4 строки фильтров — без заливки фона.** Было: приглушённый цветной фон + текст того же цвета. Стало (промежуточный шаг в этой сессии, позже пересмотрен — см. следующий раздел): прозрачный фон + полупрозрачная цветная рамка + текст цвета категории.

### Фильтры и верхний блок статистики приведены к виду "Заведующий" — вообще без цвета
Следующий шаг в той же сессии: пользователь посмотрел на промежуточный результат (п.4 выше — цветные рамка+текст без заливки) и попросил пойти дальше — убрать цвет полностью, сделать все фильтры и `.stats-bar` такими же нейтральными, как ряд "Заведующий" (`.filter-head` / `.filter-btn-all`), у которого никогда не было цветовой маркировки — только `var(--border-color)` рамка и обычный текст (`var(--text-body)`/`var(--text-primary)`, т.е. чёрный в светлой теме).

Реализовано максимально просто — **удалены** CSS-правила, красившие категории (не переписаны, а именно убраны), поскольку без них элементы и так наследуют нейтральный вид от базовых `.filter-btn` / `.filter-btn.active` / `.stat-chip` — тот же код, что уже управлял видом "Заведующий":
- Удалён весь блок `.filter-btn.filter-urgent/high/normal`, `.filter-btn.filter-stage-*`, `.filter-btn.filter-overdue/0-3/4-7/7plus/no-date` (и их `.active`-варианты) — теперь **все** кнопки фильтров (Приоритет / Этап / Срок / Заведующий) визуально неотличимы друг от друга по цвету, активное состояние — сплошная заливка `var(--accent)` + белый текст (та же генерическая `.filter-btn.active`, что раньше работала только для "Заведующего" и "Все").
- Удалены `.stat-chip-urgent/high/normal` и весь блок `.stage-primary-appointment` / `.stage-exam` / ... (7 правил) — стат-чипы наверху тоже стали монохромными, кроме итогового "N пациентов" (`.stat-chip-total`), который остаётся сплошным индиго — это не категория, а якорь-CTA, его не трогали.
- Активное состояние стат-чипа (`.stat-chip.active { box-shadow: 0 0 0 2px currentColor; }`) не менялось — раньше кольцо было в цвет категории, теперь `currentColor` = обычный текстовый цвет, кольцо стало нейтрально-тёмным/светлым по теме — тоже само собой получилось правильно, без правки.
- HTML-классы вида `filter-urgent`, `stage-exam`, `filter-stage-treatment` и т.п. **оставлены в разметке как есть** (они больше ничего не стилизуют, т.к. соответствующих CSS-правил не существует) — это осознанный компромисс: переписывать 20+ мест в JS-шаблонах ради удаления теперь-инертных имён классов не стали, риск опечатки не оправдан нулевым визуальным эффектом. Если понадобится частично вернуть цвет — эти классы-маркеры уже на месте, останется только дописать CSS.
- Карточки пациентов в списке (`priority-tint-*`, `.date-indicator-*`) **не тронуты** — вся эта правка касалась только верхнего блока статистики и 4 строк фильтров, не самих карточек.

### Панель статистики (вверху, над списком пациентов) — прошла 3 итерации, см. историю ниже
**Итерация 1** (давно): 10 больших плашек `.stat-card` в 2 колонки.
**Итерация 2**: заменено на компактный `.stats-bar` с рядами мелких кликабельных "чипов" `.stat-chip` — число+подпись в пилюле, цвета совпадали с `.priority-pill`/`.stage-*` на карточках пациента. Потом (по просьбе пользователя "без заливок, как у Заведующего") цвет убрали — чипы стали монохромными, только рамка+текст.
**Итерация 3 (текущая)** — пользователь спросил "можно в каком-то инфографичном стиле?", посмотрел 3 визуальных варианта (сегментная шкала+воронка / донат-диаграммы / текущий монохромный) через артефакт-визуализацию, выбрал **вариант с воронкой этапов + сегментной шкалой приоритета**, но попросил вернуть цвет приоритетной шкалы — **тот же rgba, что у вертикальной цветной полосы на карточке пациента** (`border-left`), а не просто произвольный "яркий" цвет.

Текущая структура `.stats-bar` (теперь `flex-direction: column`, не ряд чипов):
1. Чип "N пациентов" (`#totalStat`) — сплошной `var(--accent)`, как и раньше, единственный "якорный" цветной элемент помимо приоритетной шкалы.
2. Подпись "Приоритет" (`.stats-bar-label`) + `<div id="priorityBar" class="priority-bar">` — **3 сегмента-кнопки** (Срочно/Высокий/Обычный), ширина каждого = `flex-grow: count + 1` (пропорционально числу пациентов; `+1` — чтобы сегмент с 0 пациентов не схлопывался в невидимую полоску). Фон сегментов — **rgba(239,68,68,0.55) / rgba(245,158,11,0.55) / rgba(59,130,246,0.55)** — ровно те же значения, что у `.patient-card.priority-urgent/high/normal` (`border-left-color`). Текст — `var(--text-primary)` (тёмный/светлый по теме), читается нормально поверх этих полупрозрачных заливок в обеих темах (проверено визуально).
3. Подпись "Этапы" + `<div id="stageFunnel" class="stage-funnel">` — **7 сегментов-кнопок** в порядке `app.stageOrder`, тоже `flex-grow: count + 1`, но **монохромные** (`var(--surface-alt)` фон, `var(--text-primary)`/`var(--text-secondary)` текст) — воронка про форму потока, не про категорийный цвет, поэтому цвет здесь не нужен и был бы шумом.
4. И шкала, и воронка **кликабельны** — те же `app.filterByPriority()`/`app.filterByStage()` с тем же toggle-паттерном, что и раньше. Активный сегмент шкалы приоритета — `box-shadow: inset 0 0 0 3px rgba(0,0,0,0.35)` (тёмное кольцо поверх цветной заливки); активный сегмент воронки этапов — заливается `var(--accent)` целиком (т.к. в невыбранном состоянии там и так нет цвета, заливка при активации не создаёт диссонанса).

Вся разметка рендерится **динамически** в JS (`updateStats()`), а не статична в HTML, — потому что ширина сегментов (`flex-grow`) зависит от текущих данных. Старые статичные кнопки с ID вида `urgentChip`/`examChip`/... и вспомогательные классы `.stats-bar-divider`/`.stats-bar-group`/`.stat-chip-urgent/high/normal` удалены как мёртвый код (вместе с уже неиспользуемыми `button.stat-chip`/`.stat-chip.active` — `.stat-chip` теперь навешен только на статичный div тотала, кнопкой не является).

**Если понадобится ещё раз показать пользователю варианты дизайна** — использовался `mcp__visualize__show_widget` (артефакт-виджет), это быстрее, чем описывать словами, и работает хорошо для сравнения 2-3 макетов бок о бок.

**Итерация 4 (текущая, финал)** — пользователь спросил "что думаешь по оформлению остальных фильтров, чтобы всё смотрелось аутентично?", посмотрел ещё один набор макетов, согласился и попросил убрать дублирование целиком:
1. **"Срок до ближайшего этапа" переехал в `.stats-bar` четвёртой строкой** — `<div id="deadlineFunnel" class="deadline-funnel">`, 5 сегментов (Просрочено / 0-3 дня / 4-7 дней / более 7 дней / Дата не установлена), тоже `flex-grow: count + 1`. Цвета сегментов — **те же оттенки, что у `.date-indicator-urgent/soon/ok/nodate`** на карточке пациента (просто подняты до alpha 0.55 вместо 0.12-0.18, чтобы визуально быть на одном уровне яркости с приоритетной шкалой): `rgba(239,68,68,0.55)` для Просрочено и 0-3, `rgba(245,158,11,0.55)` для 4-7, `rgba(76,175,80,0.55)` для 7+, `rgba(148,163,184,0.4)` для "без даты". Бакеты считаются в `updateStats()` через уже существующий `getPatientDeadlineDays(p)` (те же границы, что в `getFiltered()`: `overdue` = days<0, `0-3` = 0..3, `4-7` = 4..7, `7+` = >7, `no-date` = null).
2. **Явная кнопка "Все" встроена в конец каждой из 3 строк** (`.stats-bar-reset`, id `priorityResetBtn`/`stageResetBtn`/`deadlineResetBtn`) — раньше сброс работал только повторным кликом по активному сегменту (это осталось), кнопка — подстраховка для привычного жеста. Активное состояние кнопки (`!this.priorityFilter` и т.д.) тоже обновляется в `updateStats()`.
3. **Ряды пилюль "Приоритет" и "Этап прохождения" под шапкой "Список пациентов" удалены целиком** — они дублировали шкалу и воронку сверху один в один, пользователь прямо сказал "не вижу смысла в дублировании". Строка "Срок до ближайшего этапа" тоже удалена оттуда (переехала в п.1). Из всей секции фильтров под тулбаром остался только **"Заведующий"** — воронку туда сознательно не стали делать (см. текст виджета-предложения: 8 разноразмерных фамилий плохо сжимаются в пропорциональные сегменты), но добавили счётчик пациентов в каждую пилюлю (`renderHeads()`, `<span class="count">${count}</span>`), включая "Все" (общий тотал).
4. **Мёртвый код почищен**: из `filterByPriority`/`filterByStage`/`filterByDeadline` убраны `document.querySelectorAll('.priority-filter-btn'/'.stage-filter-btn'/'.deadline-filter-btn')` — тех классов/кнопок больше нет в HTML.
5. **Responsive-баг и его фикс**: на узких экранах (мобильный, ~375px) воронка из 7 (этапы) или 5 (срок) сегментов + кнопка "Все" в одной строке — подписи типа "Направл."/"Дата не установлена" сжимались до нечитаемости. Исправлено — `.stage-funnel`/`.deadline-funnel` теперь `overflow-x: auto` (внутренняя горизонтальная прокрутка) вместо `overflow: hidden`, сегменты получили `flex-shrink: 0; min-width: 62px` (не сжимаются меньше читаемого), кнопка "Все" остаётся вне зоны прокрутки (сосед по флексу, не внутри воронки) — всегда видна. `.priority-bar` (только 3 сегмента) в этом не нуждается, у неё `overflow: hidden` как и было — на любой ширине помещается без скролла.

**Итерация 5 (текущая, финал)** — пользователь попросил сделать цвета градиентными "чтобы не смотрелось просто", затем (после первой попытки) — "слишком агрессивно, сделай помягче", плюс распространить тот же градиент на вертикальные полосы приоритета в списке пациентов. Итог — два раунда:
- **Первая попытка (откачена как слишком яркая)**: непрозрачные градиенты через яркие hex-цвета (`linear-gradient(135deg, #f87171, #b91c1c)` и т.п.) + белый текст с `text-shadow`. Пользователь счёл это агрессивным.
- **Финальная версия**: градиент **внутри одного тона** через две ступени alpha одного и того же rgba-цвета — например `.priority-bar .seg.urgent { background: linear-gradient(135deg, rgba(239,68,68,0.32) 0%, rgba(239,68,68,0.58) 100%); }` (было плоское `rgba(239,68,68,0.55)`). Текст вернулся на `var(--text-primary)` (тёмный/светлый по теме, без тени) — с таким мягким градиентом тёмный текст читается нормально, а лишний контраст (белый+тень) как раз и создавал "агрессивное" ощущение. То же для `.deadline-funnel` (urgent/soon/ok/nodate — каждому своя пара alpha-ступеней того же цвета, что был раньше). Кольцо активного сегмента упрощено обратно до `box-shadow: inset 0 0 0 3px rgba(0,0,0,0.3)` (было двойное бело-чёрное кольцо — тоже часть "слишком ярко").
- **Вертикальная полоса приоритета на карточке пациента (`.patient-card` `border-left`) теперь того же цвета, что и шкала приоритета сверху** — прямая связь, которую попросил пользователь. Технически: CSS `border-left-color` не умеет градиент (border не поддерживает `background`), поэтому реализовано через `::before`-псевдоэлемент — `border-left` оставлен, но `border-left-color: transparent` (только резервирует 9px пространства, как раньше), а `.patient-card.priority-urgent/high/normal::before` — `position:absolute; left:0; top:0; bottom:0; width:9px;` с `background: linear-gradient(180deg, rgba(H,S,0.4) 0%, rgba(H,S,0.75) 100%)` — те же rgba-оттенки (H = 239,68,68 / 245,158,11 / 59,130,246), что у `.priority-bar`, только направление вертикальное (`180deg`, сверху вниз) вместо диагонального `135deg` — логичнее для узкой высокой полосы, чем для широкого горизонтального сегмента. `.patient-card` получил `position: relative` (нужно для абсолютного позиционирования псевдоэлемента).

### Кнопки фильтров — цветовая маркировка + toggle-клик (частично устарело, см. "Итерация 4" выше)
Строк "Приоритет"/"Этап прохождения"/"Срок до ближайшего этапа" под тулбаром больше не существует (перенесены в `.stats-bar` и переосмыслены как цветные шкалы/воронки — см. выше). Актуально только для "Заведующего". Историческое описание (для контекста, как эволюционировал дизайн) — все 4 строки фильтров тогда были:
- **Окрашены по категории даже в неактивном состоянии** (приглушённый тон), при активации — насыщенная заливка тем же цветом + белый текст. Цвета переиспользуют существующие токены: приоритет — `.filter-urgent/high/normal` (те же оттенки, что `priority-pill`), этап — `.filter-stage-*` (те же оттенки, что бейдж этапа на карточке), срок — `.filter-overdue/0-3/4-7/7plus/no-date`. Кнопка "Все" в каждой строке остаётся нейтральной (белая / фиолетовый градиент при активности) — это явный "сброс", контрастирующий с цветными категориями.
- **Toggle-клик**: клик по кнопке применяет фильтр; повторный клик по уже активной кнопке сбрасывает его в "Все". Реализовано через условный аргумент прямо в `onclick`, например `onclick="app.filterByPriority(app.priorityFilter==='urgent' ? 'all' : 'urgent')"`. Для "Заведующего" (кнопки рендерятся динамически в `renderHeads()`) toggle-цель вычисляется на этапе рендера — `isActive ? 'all' : head`.
- Секции подписаны через новый класс `.filter-section-label` (uppercase, мелкий текст) вместо инлайновых стилей.

### Индикатор срока на карточке пациента — приглушён (был слишком "ярким"/рябил)
Раньше `dateIndicator` (" 2 дн. 09:30", " просрочено...", " дата не установлена") рендерился как `<div>` на всю ширину карточки со сплошной насыщенной заливкой (`background:${color}; color:white`) — визуально тяжело, особенно когда сразу несколько карточек подряд просрочены/срочны.

Теперь единая функция `renderDateIndicator(days, timeStr, extraLabel)` (заменила `getDateIndicatorColor` — тот удалён как мёртвый код) рисует компактный `inline-flex`-чип: приглушённый tint-фон + маленькая цветная точка `.date-indicator-dot` вместо сплошной заливки. Категория считается через `getDateIndicatorCategory(days)`: `urgent` (≤3 дня, включая просрочку) / `soon` (4-7) / `ok` (7+) / `nodate`.
- **Точка спокойно пульсирует** (`@keyframes gentle-pulse`, 2.4s, только `opacity` 1→0.3, без scale — чтобы не "рябило") **только для категории `urgent`**. `soon`/`ok`/`nodate` — статичные, без анимации.
- Один и тот же `renderDateIndicator()` используется во всех трёх местах, где раньше был этот индикатор: карточка в списке (`renderPatients`), бейдж события в "Подробной хронологии" (`renderHistoryLog`), статус-строка в редакторе плановой даты (`renderStageEventsPanel`) — единообразный спокойный вид везде.
- **Больше не актуально**: `treatmentBadge` ("Хирургическое лечение" и т.п.) тоже переведён на компактный стиль (см. ниже) — единообразно со всем остальным.

### Компактный тип лечения + мета-чипы (возраст/время/диагноз) на карточке пациента
- `treatmentBadge` (раньше — сплошной оранжевый full-width `<div>`) теперь `<span class="treatment-indicator">` — приглушённый tint (`#fff3e0`/`#e65100`, те же цвета что `.stage-treatment`). Т.к. это теперь `inline-flex span`, а не блочный `div`, он визуально встаёт в один ряд с `dateIndicator` (тоже `span`), а не занимает отдельную полную строку.
- Мета-строка на карточке (возраст / время с добавления / диагноз) была голым текстом через `gap` — обёрнута в мелкие нейтральные чипы `.meta-chip` (фон `var(--surface-alt)`, без цветовой маркировки — специально нейтрально, чтобы не спорить вниманием с цветными индикаторами срока/приоритета).
- **(Обновлено позже в этой же сессии, см. "Карточка пациента в списке — 2 компактные строки" ниже)** — эти чипы вместе с бейджем этапа объединены в единый ряд.

### Развёрнутая карточка пациента — данные пациента убраны за кнопку-тоггл
Раньше при разворачивании карточки шёл порядок: Личные данные → Медицинская информация → Таймлайн+хронология+сводка → Классификация (снова формы) → кнопка удаления — то есть блок с формами редактирования пациента появлялся ДО и ПОСЛЕ таймлайна, взгляд терялся при скролле.

Теперь `renderPatientDetails(p)` рендерит: цветной бейдж текущего этапа → кнопка-тоггл **"Просмотр и редактирование данных пациента"** (`app.togglePatientData(id)`, шеврон крутится 180° при раскрытии) → *если раскрыта* — единая `.patient-data-panel` (Личные данные + Медицинская информация + Классификация + кнопка "Удалить пациента", всё как было, просто объединено в один блок) → **сразу же Таймлайн** (шаги, редактор дат, "Подробная хронология", сводка, кнопка копирования — все они остаются внутри `renderTimeline(p)`, как и было).
- Состояние раскрытия — `app.expandedPatientData` (`Set`, лениво инициализируется как `expandedPatients`), не сбрасывается при точечных изменениях полей (`onchange` → `app.render()`), т.к. это persistent состояние на `app`, а не локальная переменная рендера.
- По умолчанию при разворачивании карточки панель данных **свёрнута** — сразу видно таймлайн, что и было целью правки.

### Логотип МКНЦ в шапке (вместо эмодзи-заглушки)
Пользователь прислал `OD5_logo_neg1.png` (лежит в `clinic-tracker-python/`) — это "негативная" версия (белый текст названия центра, невидим на светлом фоне), но сама иконка-шестиугольник с текстом "МКНЦ" внутри полностью в фиолетовых тонах и одинаково хорошо видна на светлом и тёмном фоне. ### Все эмодзи убраны из интерфейса
Пользователь счёл эмодзи (было ~50+ штук по всему файлу — в бейджах, фильтрах, кнопках, предупреждениях) несерьёзными для медицинского приложения. Убрано полностью, кроме нескольких **монохромных** типографских символов, которые остались как функциональная иконография (не эмодзи по сути): `✓` (галочка — пройден этап / событие состоялось), `✕` (крестик — удалить событие), `→`/`▼`/`▲` (стрелка-подсказка, шевроны разворачивания).

Что пришлось переделать, а не просто вычистить текст:
- **`app.stageNames`** — центральный объект с названиями этапов (использовался и в бейджах, и в таймлайне, и в фильтрах) — эмодзи-префиксы убраны из самих строк.
- **Иконки узлов таймлайна** — раньше брались как "первый символ" названия этапа через `stageEmoji = stageNames[stage].match(/^\S+/)` (то есть буквально эмодзи-символ). Без эмодзи-префикса это стало бы вырезать первое слово целиком. Заменено на **номер шага** (1-7) в кружке; для пройденных — по-прежнему `✓`. Тем же исправлением убрана старая функция `.replace(/^\S+\s/, '')` (тоже завязанная на "первый символ = эмодзи"), которая раньше отрезала эмодзи от подписи под кружком — теперь подпись просто выводится целиком.
- **Кнопка темы** (`#themeToggle`) была круглой 36×36px иконкой (луна/солнце) с фиксированным белым цветом текста — переделана в текстовую пилюлю ("Тёмная тема" / "Светлая тема") на `var(--surface-alt)`/`var(--text-primary)` (тема-зависимые переменные, а не хардкод).
- Попутно найден и исправлен pre-existing баг с низкой контрастностью: кнопки "Экспорт"/"Импорт" имели захардкоженный светло-серый фон (`#edf2f7`) при тема-зависимом цвете текста — в тёмной теме текст становился светлым на светлом фоне (почти нечитаемо). Заменено на `var(--surface-alt)` + рамка `var(--border-color)`.

### Сортировка по дате добавления
Выпадающий список `#sortOrderSelect` рядом с поиском: "по умолчанию" (порядок как в массиве, т.е. по возрастанию — старые сначала), "Сначала новые", "Сначала старые". Состояние — `app.sortOrder` (`null` / `'newest'` / `'oldest'`), применяется в `getFiltered()` после всех фильтров, сортирует по полю `p.arrival`.

### Фильтр по сроку до ближайшего этапа
Строка фильтров "Срок до ближайшего этапа:" (после "Заведующий:"): Все / Просрочено / 0-3 дня / 4-7 дней / более 7 дней / Дата не установлена. Считается через `getPatientDeadlineDays(p)` — дни до `date` последнего события текущей occurrence (та же логика, что красит цветной "чип" под каждой карточкой пациента). Просроченные (`days < 0`) — отдельная корзина **Просрочено**, не смешана с 0-3. Пациенты без установленной плановой даты (`days === null`) — отдельная корзина **Дата не установлена** (это могут быть и пациенты на этапах без плановой даты вообще, например "Первичный прием"/"Завершил лечение").

### Импорт / экспорт данных о пациентах (JSON)
Кнопки "Экспорт" / "Импорт" в шапке списка пациентов:
- **Импорт** (`app.triggerImport()` → скрытый `<input type="file" id="importFileInput">` → `app.handleImportFile()`) — читает JSON-файл, проверяет что это массив, спрашивает подтверждение (`confirm`), затем **мёржит** по `id`: пациенты с совпадающим `id` перезаписываются данными из файла, остальные добавляются. Существующие "чужие" пациенты, которых нет в импортируемом файле, не удаляются. Так на другом устройстве/браузере можно скинуть файл коллеге и объединить списки, не боясь потерять его локальные данные.
- **Экспорт — теперь с выбором пациентов** (не сразу скачивает всех). Кнопка "Экспорт" → `app.openExportModal()` → открывает `#exportModal` со списком пациентов с чекбоксами. Задумано для передачи части пациентов другому врачу на время отпуска/больничного — заведующий/врач ищет своих пациентов и экспортирует только их, а не всю базу.
  - **Поиск в модалке** ищет и по ФИО пациента, и по ФИО заведующего (`p.name` ИЛИ `p.head`) — так можно быстро набрать "всех пациентов заведующего X" через строку поиска + "Выбрать все".
  - **"Выбрать все" / "Снять все"** оперируют только над **текущим отфильтрованным** списком (не над всеми пациентами вообще) — id видимых строк кладутся в `data-filteredIds` на `#exportPatientList` при каждом рендере, так что "Выбрать все" после поиска не подхватывает пациентов, скрытых фильтром.
  - Выбор хранится в `app.exportSelectedIds` (`Set`, лениво инициализируется в `openExportModal()`), переживает смену поискового запроса (не сбрасывается при перерендере списка).
  - `app.confirmExport()` — если ничего не выбрано, `alert` с просьбой выбрать хотя бы одного и не закрывает модалку; иначе фильтрует `app.patients` по выбранным id и скачивает через новый общий хелпер `app.downloadPatientsAsJson(list)` (старая `exportPatients()` переименована/обобщена под этот хелпер, чтобы можно было скачивать и подмножество, и весь список).
  - Модалка `#exportModal` закрывается по клику на фон (тот же mousedown/click-паттерн против случайного закрытия при drag-выделении текста, что и у `#addModal`) или кнопкой "Отмена".

## Другие известные ограничения
- **Конфиденциальность**: пароли в открытом JS, доступ через консоль браузера тривиален — не для реальных пациентов без доработки
- **Данные не расшариваются** автоматически между устройствами/браузерами — каждый видит свою локальную копию, но теперь можно вручную обменяться JSON-файлом через экспорт/импорт (см. выше)
- Решение по общей онлайн-версии (Supabase рекомендован) — отложено, не реализовано
