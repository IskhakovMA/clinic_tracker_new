# Три recovery-оператора и ограниченная offline ceremony

Статус: синтетическая модель + предложение для реализации. Реальные лица, сроки, устройства и юридические полномочия не назначены.

## Онлайн-процесс

Ровно три независимо назначенных оператора A/B/C; восстановление сотрудника требует двух различных действующих операторов. Оператор-цель не голосует: A восстанавливают B+C. Два недоступны → онлайн recovery невозможно. Третий не заменяется дежурным администратором автоматически. Developer-роль сама по себе не должна давать recovery-authority: в новой модели это отдельное назначение, не общая RBAC-перестройка.

Каждый approval требует свежего password+WebAuthn UV/step-up, связан с case/action/target/epoch/policy/generation и сроком. При finalize под write lock заново проверяются оба оператора, их полномочия, epochs и исключение цели. UNIQUE(case,actor) запрещает повторное голосование. Смена роли/статуса/epoch аннулирует старое одобрение; отзыв полномочий проверяется до выдачи. Одновременные approvals сериализуются, выдача ровно одна. Нет медицинского допуска от recovery-кода или решения операторов.

В модели `Recovery`: два approval + audit + increment target epoch + EnrollmentOnly grant фиксируются одной транзакцией. SIGKILL перед grant откатывает второй approval и выдачу; первый остается. Audit failure не выдает grant. Grant — случайный bearer, в базе hash, связан с целью/epoch, одноразовый, ограниченный временем; не принимается медицинским API. Потерянный ответ после commit требует нового контролируемого случая/отзыва, не извлечения bearer из БД. Значения 600/300 секунд — исключительно параметры эксперимента, не утвержденная эксплуатационная политика.

Полная реализация должна в той же атомарной операции отзывать факторы, sessions, challenges и старые recovery-коды цели (это уже проверяется прежней `Engine`-моделью); новая `Recovery` намеренно не имеет таблицы медицинских сессий. Эти две модели не являются готовой интегрированной auth-системой. Новый фактор активируется только после отдельной регистрации, доказательства владения и подтвержденного уведомления; два физически/операционно независимо доступных фактора должны быть квалифицированы, два credentials одного устройства не доказывают независимость.

## Потеря всех операторов / S1 всех учетных записей

Требуется утвержденная offline ceremony, а не автоматическая команда:

1. Остановить все app/workers, исключительные блокировки, проверить происхождение backup/permit/witness и сохранить доказательства. DB verify отдельно от security trust.
2. Собрать независимую offline authority по утвержденному владельцем составу и двухстороннему контролю. Это не действующие онлайн-операторы, которые сами могут быть заблокированы. Установить личности, полномочия и основания восстановления вне восстановленной БД. Без доступного кворума — оставаться в hold.
3. Зафиксировать конкретный installation UUID, актуальный внешний sequence или явно признать его потерю и применить полную reproof-процедуру. Уничтожить восстановленные sessions/flows/grants/codes, повысить security/auth epochs, зафиксировать инцидент с обязательным аудитом. Не объявлять старые факторы доверенными только потому, что они есть в backup.
4. Выдать только ограниченное, адресное, одноразовое EnrollmentOnly разрешение для первичного оператора. Никаких общих паролей, MFA-disable флагов, медицинской сессии или общего reusable emergency-token. Проверить новые факторы и независимое уведомление.
5. Последовательно восстановить три независимых операторских назначения по утвержденной ceremony, проверить взаимную недоступность/self-approval и только затем обычные recovery. Возобновлять медицинский доступ по отдельному полному password+WebAuthn входу при снятых DB/security holds.
6. Независимый разбор и сверка аудита. Инструмент ceremony должен иметь typed explicit evidence, ограничение цели/поколения/одноразового nonce, аудит и отказ при любой неопределенности. **В этом прототипе такого инструмента нет**; нельзя заменить процедуру UPDATE trust.

Не утверждены: состав offline authority, способ независимого удостоверения личности/уведомления, custody носителей, кворум при катастрофе, SLA/сроки, фактическая независимость трех операторов. До этих решений полное MFA включать нельзя. Недоступность двух операторов — осознанный отказ, а не повод вводить обход.
