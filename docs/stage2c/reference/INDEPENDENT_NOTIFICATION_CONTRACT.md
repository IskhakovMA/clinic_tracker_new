# Контракт независимых уведомлений, draft 1

Для first_factor, add_factor, revoke_factor и recovery создается отдельное уведомление, связанное с installation/user UUID, action/case, auth_epoch, policy, generation, event ID и сроком. Payload без медицинских данных, пароля, challenge, recovery bearer или приватного ключа. Контактный канал нельзя менять в той же recovery-операции без независимого подтверждения прежнего доверенного канала или offline ceremony.

| Состояние | Доказательство | Что не считается доказательством |
|---|---|---|
| CREATED | Атомарная запись намерения и security audit | Отправка/доставка |
| TRANSMISSION_INITIATED | Уникальный dispatch ID, попытка передачи | Отметка оператора «доставлено» |
| INDEPENDENT_DELIVERY_CONFIRMED | Проверенная receipt отдельного доверенного канала, точная привязка, уникальность и freshness | HTTP 200 провайдера, enqueue, локальная квитанция того же оператора |
| EMPLOYEE_ACKNOWLEDGED | Независимая проверка личности сотрудника и привязка к конкретному событию/receipt | Операторский approval, нажатие в скомпрометированной pre-auth сессии |
| DISPUTED / UNAUTHORIZED | Зафиксированный спор; security hold, отзыв grants/flows/sessions через epoch | Автоматическое закрытие или resend, стирающее спор |

В эксперименте это независимые поля, не один ack-bit: created/sent/receipt/employee ack/dispute. При споре повышается epoch, прежние подтверждения больше не действуют. Квитанция уникальна и не переносится на другое событие/сотрудника/epoch. Для recovery без receipt И employee acknowledgement grant не выдается. При добавлении/первом факторе до подтверждения новый фактор остается pending, полноценной сессии нет. При отзыве ключа **сам отзыв выполняется немедленно**: ожидание уведомления не продлевает действие отозванного ключа; отсутствие подтверждения удерживает последующие enrollment/recovery и требует инцидент-процедуры. Если все каналы утрачены, применяется отдельная offline ceremony, не фиктивная отметка доставки.

`Recovery.delivery()` принимает **синтетический evidence object из доверенного тестового boundary**, не делает реальную верификацию подписи/провайдера. `acknowledge()` получает уже удостоверенного тестового principal; нет эндпоинта, принимающего такую структуру от клиента. Во время потери факторов доказательство личности для acknowledgement должно поступать из независимой утвержденной ceremony; обычный pre-auth или знание пароля недостаточны. Строка issuer в модели не является настоящей аутентификацией отправителя. Модель доказывает переходы/отказы, не независимость реального канала.

Перед внедрением выбрать канал и доверенную сторону, защиту ключей/receipt, challenge-response подтверждения сотрудника, анти-replay, устойчивую доставку и подтверждение отказов, таймауты и escalation, privacy/retention и порядок споров. Сейчас никакие SMS/email/API не подключены; провайдер не выбран. Принудительная доставка не может быть обещана без инфраструктуры. Fail-closed оставляет сотрудника в EnrollmentOnly/hold и инициирует контролируемую процедуру, не снимает MFA.
