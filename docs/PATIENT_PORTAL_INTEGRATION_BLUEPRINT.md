## 1. Цель

Превратить Patient Portal из автономной демонстрации в мобильного клиента «Системы планирования»: пациент видит **свою настоящую карточку**, маршрут, записи и уведомления, ведёт переписку с врачом, с которым у него есть подтверждённая системой связь.

Документ фиксирует фактическое состояние обеих систем, определяет границу Patient API, модель идентичности и аутентификации, и предлагает поэтапный план. Это **не** разрешение начинать реализацию — порядок этапов и открытые вопросы требуют решения владельца.

## 2. Текущее состояние Clinic Tracker

### 2.1. Архитектура

FastAPI + SQLite (схема версии 9), frontend — статический SPA, который отдаёт тот же процесс. Один экземпляр, одна база, запуск по умолчанию на `127.0.0.1:8420`. 58 тестовых файлов, 458 тестовых функций. CI: один workflow `ci.yml`.

Зарегистрированные роутеры: `auth`, `ai`, `patients`, `importexport`, `migrate`, `audit_log`, `data_quality`, `notifications` (+ templates), `analytics`, `internal_notifications`, `staff`, `structure`.

### 2.2. Таблицы (полный список схемы)

`schema_version`, `app_login`, `roles`, `users`, `departments`, `user_departments`, `department_heads`, `sessions`, `patients`, `history_entries`, `events`, `patient_diagnosis_history`, `future_plans`, `audit_events`, `patient_notification_preferences`, `notification_templates`, `notifications`, `internal_notification_state`, `patient_attention_issues`.

### 2.3. Ответы на вопросы задания

**1. Как создаётся пациент.** `POST /api/patients` → `store.create_patient()`. Обязательные поля: `name`, `priority`, `stage`, `diagnosis` (min 1 символ), `head`. Лечащий врач назначается через `policy.resolve_create_doctor()`. При создании заводится первая запись `history_entries` с текущим этапом. Локализация и диагноз проверяются на согласованность (`localization_catalog.validate_new_combination`).

**2. Authoritative patient ID.** `patients.id` — `TEXT PRIMARY KEY`, значение `uuid.uuid4().hex` (`store.new_id()`). Генерируется сервером, не содержит персональных данных, используется во всех внешних связях (`history_entries`, `notifications`, `audit_events.patient_id`, `patient_attention_issues`). **Это единственный authoritative идентификатор пациента.** Номер полиса ОМС (`policy_number`) — обычное поле, не ключ, не уникален.

**3. Где хранится телефон.** `patients.phone TEXT` (nullable). Нормализация — `backend/app/phone.py`: только цифры, `8` → `7`, допустимая длина 10–15 цифр. Телефон используется очередью SMS-уведомлений и правилом качества данных `invalid_phone`.

**4. Email пациента.** **Отсутствует полностью.** Поиск по всему `backend/app` даёт ноль вхождений слова `email`. Ни колонки, ни модели, ни валидации. Это первое и главное отсутствующее звено для предлагаемой бизнес-логики.

**5. Кто создаёт/изменяет пациента.** `policy.can_create_patient` / `can_write_patient`: роли со стратегией `global` (`developer`), `by_department` (`department_head` — в своих отделениях), `by_treating_doctor` (`doctor` — только свои). Роли `deputy_chief_oncology` и `caop_head` — `global_readonly`, любая запись отклоняется 403.

**6. Кто изменяет контактные данные.** Отдельного права нет. Телефон меняется через `PATCH /api/patients/{id}` (`PatientFieldUpdateIn.field = "phone"`), то есть **любой ролью с правом записи на этого пациента**. Согласие на SMS (`PUT /api/notifications/patients/{id}/preferences`) защищено тем же `_require_patient_write`. Это и есть существующий образец «кто управляет контактом пациента».

**7. Как определяется лечащий врач.** `patients.treating_doctor_user_id → users.id`. Это authoritative связь. Текстовые поля `doctor` и `head` — отображаемые, для legacy-записей без сопоставления. Смена врача — `PUT /api/patients/{id}/treating-doctor`, право `policy.can_change_treating_doctor` (только `developer`).

**8. Как пациент связан с маршрутом.** `history_entries` — упорядоченные (`seq`) вхождения в этап, у каждого `stage`, `entered_at`, `checklist_json`, `note`. Этапы (`models.STAGES`): `primary-appointment`, `exam`, `appointment`, `consult`, `treatment-prep`, `treatment`, `completed`, `dispensary-observation`, `diagnosis-not-confirmed`. Последние три — терминальные.

**9. Как хранятся записи (приёмы).** Отдельной сущности «запись на приём» **нет**. Приём — это строка `events`, привязанная к `history_entry_id`, с полями `date`/`time` (план) и `actual_date`/`actual_time` (факт), `treatment_type`, `consilium_decision`. Есть `future_plans` — плоские плановые даты по шаблону. **Расписания, слотов, доступности и ёмкости в системе нет** — поиск по `slot`/`availability`/`capacity` даёт только очередь уведомлений (`notifications.scheduled_at`).

**10. Какие документы существуют.** **Никаких.** Ни таблицы, ни загрузки файлов: `UploadFile` и `multipart` в backend не встречаются ни разу. Единственная работа с файлами — импорт/экспорт JSON и шифрованные резервные копии БД.

**11. Что можно переиспользовать.** Серверная политика доступа (`policy.py`) — готовый, протестированный механизм ограничения выборок; аудит (`audit.py`, обезличенный, ~50 типов событий); очередь уведомлений (`notifications`), пригодная как транспорт для будущей доставки OTP, если заменить провайдера; Argon2id и rate limiting (`security.py`); модель сессий как образец (не как готовое решение — см. 5.2).

### 2.4. Messaging и patient-facing auth

**Отсутствуют полностью.** Нет таблиц диалогов/сообщений, нет учётных записей пациентов, нет patient-сессий. `users` — это исключительно сотрудники (`username` + Argon2id-хеш + роль). `/api/auth/*` обслуживает только персонал: `login`, `logout`, `me`, `change-password`.

## 4. Patient Identity

> **Реализовано в Stage 1.** Фактическая схема, права и endpoints — в разделе 21.

### 4.1. Опорный факт

Единственный authoritative идентификатор — `patients.id` (UUID). Email у пациента в системе нет. Значит, **связь «мобильный пользователь ↔ карточка» нужно создавать как новую сущность**, а не выводить из существующих полей.

### 4.2. Предлагаемая модель (минимальная)

Новая таблица `patient_portal_access` (одна строка на карточку, не больше):

| Поле | Назначение |
|---|---|
| `patient_id` | PK, FK → `patients.id` ON DELETE CASCADE |
| `email_normalized` | нормализованный адрес, UNIQUE; **один email — не более одной карточки** |
| `status` | `invited` / `active` / `suspended` / `revoked` |
| `linked_at`, `linked_by_user_id` | кто и когда привязал |
| `activated_at` | когда пациент завершил активацию |
| `enrollment_state` | состояние 2FA: `none` / `totp_enrolled` |
| `last_login_at` | для операционного контроля |

Телефон как альтернативный канал использовать можно (`patients.phone` уже есть и нормализован), но он не уникален и не проверен — поэтому **первичный идентификатор доступа — email**, телефон только как дополнительный фактор доставки.

### 4.3. Почему именно так

- Не меняет `patients` и не трогает authoritative ID.
- Не вводит «второй реестр пациентов»: доступ — атрибут существующей карточки.
- Делает отзыв доступа отдельной операцией, не связанной с удалением карточки.
- Позволяет аудировать привязку отдельным типом события.

### 4.4. Кто чем управляет

Новая роль **не нужна**. В системе уже есть ровно тот слой прав, который для этого годится: право записи на конкретного пациента (`can_write_patient`). Но «привязать мобильный доступ» — операция более чувствительная, чем правка телефона, поэтому предлагается **новое право внутри существующих ролей**, а не новая роль.

| Операция | Кто | Обоснование |
|---|---|---|
| Привязать email | `developer`, `department_head` (в своём scope) | Это административное действие по идентификации человека; врач ведёт лечение, а не выдаёт учётные доступы |
| Изменить email | те же | Смена идентификатора доступа = фактически выдача доступа другому адресу |
| Отвязать email / отключить доступ | те же + **`doctor` для своих пациентов** | Прекращение доступа должно быть доступно быстрее, чем выдача: это защитное действие |
| Сбросить enrollment (TOTP/recovery/устройства) | `developer`, `department_head` | Эквивалент сброса пароля сотруднику, который уже закреплён за `developer` |
| Просмотр состояния доступа | все роли с правом чтения пациента, включая `global_readonly` | Руководителю нужно видеть охват, не меняя его |

Открытый вопрос для владельца: нужно ли `caop_head` право привязки (он `global_readonly`, то есть сейчас физически не может ничего записать). Если ЦАОП по процессу выдаёт доступы при первичном обращении — потребуется либо отдельное точечное право, либо смена стратегии роли. Решать это должен владелец процесса, а не разработчик.

## 5. Authentication: demo → production

### 5.1. Карта замены

| Шаг | Сейчас (demo) | Production-компонент | Где должен жить |
|---|---|---|---|
| Ввод email | локальное сохранение | нормализация + поиск в `patient_portal_access` | backend |
| Eligibility | отсутствует | проверка `status = invited/active`; **единый ответ независимо от результата** | backend |
| OTP | константа `240915` | генерация, хеширование, TTL, лимит попыток, доставка | backend + провайдер доставки |
| TOTP enrollment | секрет в коде | секрет генерируется и хранится на сервере, выдаётся один раз в момент привязки | backend |
| TOTP verification | на устройстве | на сервере, с окном ±1 шаг и защитой от повторного использования шага | backend |
| Recovery codes | локальная генерация | генерация на сервере, хранение **только хешей**, одноразовое погашение | backend |
| Сессия | локальный флаг | серверная сессия с коротким access и отзываемым refresh | backend |
| Trusted device | статический список | запись устройства на сервере, привязанная к сессии; отзыв = инвалидция | backend |
| Биометрия | `BiometricGate` | **остаётся на устройстве**: локальная разблокировка хранимого refresh-токена, не фактор аутентификации для сервера | mobile |
| Locked state | локальный таймаут | остаётся локальным | mobile |

### 5.2. Почему существующий механизм сессий нельзя взять как есть

`security.create_session` выдаёт непрозрачный токен, хранит его SHA-256, привязывает к хешу пароля (смена пароля инвалидирует сессии) — это хорошая основа. Но:

- Сессия привязана к `users.id`. У пациента учётной записи в `users` нет и, по модели выше, быть не должно. Нужна **отдельная таблица patient-сессий** с FK на `patients.id`, иначе «пациент» становится сотрудником с ролью, и вся матрица RBAC поедет.
- Транспорт — cookie + CSRF-cookie. Для мобильного клиента это неудобно и небезопасно по умолчанию; нужен `Authorization: Bearer` и отсутствие CSRF-логики на patient-эндпоинтах (CSRF не применим без cookie).
- TTL 8 часов без refresh. Мобильному приложению нужен короткий access (минуты) + долгий отзываемый refresh, иначе биометрическая разблокировка превращается в фикцию.

### 5.3. Доставка OTP — нерешённый вопрос

В системе есть очередь уведомлений, но **только канал `sms`** (`CHECK (channel IN ('sms'))`) и **только mock-провайдер**. Реальной отправки нет ни по SMS, ни по email. Значит:

- Либо добавляется канал `email` и реальный SMTP/сервис — это отдельная согласованная интеграция;
- Либо OTP доставляется по SMS на `patients.phone` — но тогда email остаётся лишь идентификатором, а фактический фактор владения — телефон, и требование «подтверждение email» не выполняется.

Без решения этого вопроса production-аутентификация невозможна. Это **блокер Stage 2**.

## 6. Patient API

Принцип: не проектировать API ради API. Ниже только то, без чего мобильный клиент не работает. Отдельный префикс `/api/patient/*`, отдельная аутентификация, **полностью отдельная от `/api/*` для персонала**.

Легенда колонки «Аналог»: **есть** — можно переиспользовать сервис; **частично** — данные есть, представление другое; **нет** — сущности не существует.

### AUTH

| Endpoint | Нужен | Аналог | Источник данных | Авторизация |
|---|---|---|---|---|
| `POST /api/patient/auth/start` (email → OTP) | да | нет | `patient_portal_access` | публичный, жёсткий rate limit, единый ответ |
| `POST /api/patient/auth/verify-otp` | да | нет | новая таблица OTP-челленджей | публичный + лимит попыток |
| `POST /api/patient/auth/totp/enroll` | да | нет | `patient_portal_access` | только внутри активационной сессии |
| `POST /api/patient/auth/totp/verify` | да | нет | — | активационная/повторная сессия |
| `POST /api/patient/auth/recovery/verify` | да | нет | хеши кодов | как TOTP |
| `POST /api/patient/auth/session/refresh` | да | частично (`sessions` как образец) | patient-сессии | refresh-токен |
| `POST /api/patient/auth/logout` | да | частично | patient-сессии | access-токен |
| `GET/DELETE /api/patient/auth/devices` | да | нет | таблица устройств | access-токен |

### PATIENT

| Endpoint | Нужен | Аналог | Источник | Авторизация |
|---|---|---|---|---|
| `GET /api/patient/profile` | да | частично (`store.patient_to_dict`) | `patients` | только своя карточка |

## 7. Authorization (patient scoping)

Ключевое правило: **patient-эндпоинт никогда не принимает `patient_id` из запроса**. Идентификатор берётся только из проверенной сессии. Любой путь вида `/api/patient/patients/{id}/...` не должен существовать — это устраняет целый класс IDOR/BOLA до написания кода.

Для вложенных ресурсов (сообщение, документ, запись) проверка двухступенчатая: ресурс существует → ресурс принадлежит пациенту из сессии. Ответ при несовпадении — **404, а не 403** (как уже сделано для персонала в `_not_found()`), чтобы чужой идентификатор нельзя было подтвердить.

Персональная и пациентская авторизация не должны делить один слой: `policy.patient_scope_filter` рассчитан на сотрудников. Для пациента нужен отдельный, намеренно примитивный предикат «`patient_id` = `session.patient_id`», который невозможно расширить параметрами запроса.

## 8. Doctor ↔ Patient

### 8.1. Что уже есть

Единственная authoritative связь — `patients.treating_doctor_user_id → users.id`. Косвенные: через `events` (кто вёл приём — **не хранится**, у события нет врача) и через отделение (`user_departments`). То есть на сегодня у системы есть ровно одна надёжная связь: **лечащий врач**.

### 8.2. Предлагаемое отображение на модель приложения

| Модель приложения | Источник в системе | Доступно сейчас |
|---|---|---|
| `ASSIGNED_CARE_TEAM` | `treating_doctor_user_id` | **да** |
| `APPOINTMENT_DOCTOR` | врач конкретного приёма | **нет** — `events` не хранит врача |
| `EXPLICIT_PATIENT_LINK` | явная связь, заведённая сотрудником | нет, потребуется таблица |

Вывод: на старте messaging можно строить **только на лечащем враче**. Это ограничение, а не недостаток: оно совпадает с правилом «не поиск врача, а существующая связь».

### 8.3. Правила диалога

- **Разрешено писать**: есть активная связь (пациент имеет `treating_doctor_user_id`) и карточка не в терминальном этапе.
- **Read-only**: связь прекратилась (сменился лечащий врач, маршрут закрыт — `completed`, `dispensary-observation`, `diagnosis-not-confirmed`). История остаётся видимой пациенту, отправка запрещена. Это уже реализовано в UI (`ConversationStatus.READ_ONLY`).
- **Прекращение связи**: смена `treating_doctor_user_id` закрывает диалог со старым врачом (read-only) и открывает возможность диалога с новым.
- **Кто инициирует**: обе стороны, но только в рамках существующей связи. Пациент не выбирает врача.
- **После завершения маршрута**: все диалоги становятся read-only. Исключение для диспансерного наблюдения (пациент наблюдается годами) — **открытый вопрос к владельцу**.

Нерешённое: у врача сейчас нет рабочего места для переписки. Messaging требует интерфейса и на стороне «Системы планирования», иначе сообщения пациентов некому читать. Это удваивает объём этапа и должно быть учтено в планировании.

## 12. Documents

Проектируется с нуля. Минимальные требования:

- Хранение **вне БД** (файловая директория или объектное хранилище), в БД — только метаданные и путь/ключ.
- Скачивание только через эндпоинт с проверкой владельца; никаких прямых URL на файловое хранилище.
- Проверка типа по содержимому, а не по расширению (клиентская валидация в приложении — удобство, не защита).
- Антивирус/контентная проверка: **обязательна**, если пациент может загружать файлы, которые откроет сотрудник. Без этого загрузка превращается в канал доставки вредоносного файла на рабочее место врача.
- Аудит: загрузка, скачивание, удаление — с идентификатором документа, без имени файла (имя может содержать ФИО и диагноз).
- Лимиты: приложение уже ограничивает 5 файлов / 20 МБ; сервер обязан проверять то же самостоятельно.

Поле `Attachment.remoteId` в приложении уже предусмотрено — миграция с локального кеша на серверное хранение не ломает модель.

## 13. Security boundary

```
Мобильное приложение
        │  TLS, Bearer access-token
        ▼
  Patient API  (/api/patient/*)   ← отдельная аутентификация, отдельный scoping
        │
        ▼
Существующие сервисы (store, policy, notifications, audit)
        │
        ▼
   SQLite + файловое хранилище
```

Правила:

| Аспект | Решение |
|---|---|
| Аутентификация | Bearer access (короткий) + refresh (отзываемый), серверные patient-сессии |
| Авторизация | `patient_id` только из сессии; запрет на приём идентификатора из запроса |
| IDOR/BOLA | Двухступенчатая проверка владения + 404 вместо 403 |
| Rate limiting | Жёсткий на `auth/start` и `verify-otp`; общий на patient-API. **Текущий лимитер — в памяти процесса**, для нескольких экземпляров не годится |
| Enumeration | Единый ответ и единое время на `auth/start` независимо от существования email |
| PII | Отдельный узкий сериализатор профиля; `complaint`, `pgi_*`, `consilium_code`, внутренние заметки пациенту не отдаются |
| Аудит | Новые типы событий для привязки доступа, входа пациента, скачивания документа — без PII |
| Логи | Запрет на запись email, телефона, тела сообщений и имён файлов |
| Ошибки | Уже есть единый обработчик исключений; patient-API не должен раскрывать детали |

**Инвариант, который надо проверять тестами, а не рассуждениями**: пациент A не получает ни карточку, ни маршрут, ни записи, ни документы, ни уведомления, ни сообщения, ни список врачей пациента B. Для каждого patient-эндпоинта — негативный тест с чужим идентификатором.

## 14. Deployment

Сейчас система **не развёрнута**: `CLINIC_HOST` по умолчанию `127.0.0.1`, `CLINIC_HTTPS=false`, `TrustedHostMiddleware` разрешает только localhost. То есть сервер сегодня физически недоступен извне, и это правильное состояние для системы без развёртывания.

Предполагаемая схема:

```
Интернет → reverse proxy (TLS, rate limit) → Patient API → сервисы → БД/хранилище
                                                   ▲
                      внутренняя сеть ──────────────┘
                      (рабочие места персонала, /api/*)
```

- Публичным становится **только** `/api/patient/*`. Персональный интерфейс и `/api/*` остаются во внутренней сети.
- TLS обязателен; `CLINIC_HTTPS=true` и корректный `TrustedHostMiddleware` — предусловие, а не опция.
- CORS не нужен (мобильный клиент — не браузер); добавлять его нельзя.
- Секреты (ключи подписи токенов, учётные данные провайдера доставки) — вне репозитория.
- Резервное копирование уже есть (шифрованный формат, AES-256-GCM), но файловое хранилище документов в него не входит — потребуется расширение.

**Инфраструктура не выбрана.** Хостинг, размещение, политика ПДн, мониторинг — всё это открытые вопросы (раздел 18). Угадывать их здесь было бы вредно.

## 16. Stage plan

### Stage 0 — Решения владельца (блокирующий) — **ЗАКРЫТ 2026-10-07**
**Цель**: закрыть вопросы, без которых любая реализация будет переделана.

**Цель**: связать человека с карточкой, не трогая аутентификацию.

**Файлы**: `backend/app/db.py` (миграция), `models.py`, `policy.py`, новый `routes/portal_access.py`, `audit.py`, `static/app.js`, `index.html`.
**Зависимости**: Stage 0 (кто выдаёт доступ).
**Готовность**: сотрудник привязывает email, видит статус, отзывает; негативные тесты на чужой scope; аудит без PII.
**Security review**: да. **UI review**: да (интерфейс персонала).

### Stage 2 — Production authentication — **ЗАБЛОКИРОВАН** (нет решения по почтовому провайдеру)
**Цель**: настоящий вход пациента.
**Реализуем**: OTP-челленджи, TOTP на сервере, recovery-хеши, patient-сессии (access/refresh), реестр устройств, rate limiting, доставка OTP.

**Готовность**: полный цикл входа с устройства; отзыв сессии действует немедленно; тесты на enumeration и перебор.
**Security review**: обязателен и углублённый. **UI review**: да (экраны активации уже есть, меняются тексты и ошибки).

### Stage 3 — Профиль, маршрут, Home
**Цель**: пациент видит свои настоящие данные.
**Реализуем**: узкий сериализатор профиля, `/route`, `/events`; в приложении — сетевой слой (появляется `INTERNET`, HTTP-клиент, модели), замена `MockPatientPortalRepository`.
**Зависимости**: Stage 2; решение по объёму медданных.
**Готовность**: данные совпадают с карточкой в системе; негативные тесты на чужой `patient_id`; офлайн-поведение определено.
**Security review**: да (первая выдача медданных наружу). **UI review**: да.

### Stage 4 — Каталог, затем записи
**4a. Каталог**: серверный снимок, версионирование, кеш в приложении. Не зависит от расписания, можно делать сразу после Stage 3.
**4b. Записи (чтение)**: показ назначенных приёмов из `events`.
**4c. Самозапись**: **только если Stage 0 подтвердил необходимость** и спроектировано расписание. Иначе `DemoBookingRepository` вырезается из production-сборки, а раздел остаётся в режиме чтения.
**Готовность 4c**: созданная пациентом запись видна персоналу как `events` в маршруте.

### Stage 5 — Связь врач/пациент и messaging
**Цель**: переписка в рамках существующей связи.
**Реализуем**: вычисление связи из `treating_doctor_user_id`, таблицы диалогов и сообщений, **рабочее место врача в веб-интерфейсе**, правила read-only.
**Зависимости**: Stage 3.
**Готовность**: пациент пишет только своему врачу; смена врача переводит диалог в read-only; сообщения не попадают в аудит и логи.
**Security review**: да. **UI review**: да, с обеих сторон.

### Stage 6 — Документы и вложения
**Цель**: обмен файлами.
**Реализуем**: хранилище, метаданные, загрузка/скачивание с проверкой владельца, проверка содержимого, антивирус, аудит; в приложении — `remoteId`.
**Зависимости**: Stage 5 (вложения в сообщениях) + решение по хранилищу.
**Готовность**: чужой документ недоступен; вредоносный файл отклонён; скачивание аудируется.
**Security review**: обязателен. **UI review**: да.

### Stage 7 — Уведомления и push
**Цель**: пациент узнаёт об изменениях.
**Зависимости**: Stage 3; выбор push-провайдера (новый внешний канал — отдельное согласование ПДн).
**Готовность**: уведомление не содержит медданных в теле push.

### Stage 8 — Hardening, развёртывание, нагрузка
**Цель**: эксплуатационная готовность.
**Реализуем**: общий rate limiter (текущий в памяти не годится для нескольких экземпляров), мониторинг, оценка SQLite → PostgreSQL, нагрузочное тестирование, бэкап хранилища документов, полный security audit.

## 17. Risks

1. **Доставки OTP не существует** — ни email-канала, ни реального провайдера. Без неё Stage 2 не стартует.
2. **Расписания не существует** — самозапись из приложения сегодня невозможна в принципе. Если ожидание обратное, это надо снять до планирования сроков.
3. **Demo-запись вводит пациента в заблуждение** — если `DEMO_BOOKING` попадёт в production-сборку, пациент решит, что записан. Вырезать до первого внешнего релиза.
4. **Messaging без рабочего места врача** — сообщения будет некому читать; объём этапа вдвое больше, чем выглядит со стороны приложения.
5. **SQLite и одноэкземплярность** — patient-API делает нагрузку внешней и непредсказуемой; текущий rate limiter в памяти процесса не масштабируется.
6. **Публикация наружу меняет модель угроз целиком** — сегодня система живёт на localhost, и значительная часть её безопасности держится на этом.
7. **Объём медданных в приложении** — диагноз, ПГИ, решение консилиума на устройстве пациента: юридический и этический вопрос, не технический.
8. **Загрузка файлов пациентом** — канал доставки вредоносного содержимого на рабочее место врача без антивируса.
9. **Email как идентификатор** — общий семейный ящик даёт доступ не тому человеку; нужна политика (один email — одна карточка заложена в модели, но процесс должен её поддержать).

## 18. Open questions

1. **Канал доставки OTP**: email (нужен новый канал и провайдер) или SMS на существующий телефон? Блокирует Stage 2.
2. **Что пациент вправе видеть**: диагноз, код МКБ, результат ПГИ, решение консилиума — целиком, частично или только этапы маршрута? Блокирует Stage 3.
3. **Кто выдаёт мобильный доступ** по процессу клиники: регистратура, ЦАОП, заведующий, лечащий врач? Влияет на права в Stage 1. Отдельно: нужно ли право роли `caop_head`, которая сейчас полностью read-only.
4. **Нужна ли самозапись** пациента вообще, или приложение — только информирование? Определяет судьбу Stage 4c и всей подсистемы расписания.
5. **Источник истины для цен и услуг**: внутренняя выгрузка или ручное обновление снимка?
6. **Инфраструктура развёртывания**: где размещается, кто администрирует, как выполняются требования к ПДн? Блокирует Stage 8 и влияет на Stage 2.
7. **Диспансерное наблюдение и messaging**: остаётся ли переписка активной после завершения лечения?
8. **Хранилище документов**: файловая система или объектное хранилище; кто обеспечивает антивирус.
9. **Push-провайдер**: FCM означает передачу метаданных третьей стороне — согласовано ли.
10. **Регламент отзыва доступа**: что происходит при смерти пациента, отзыве согласия, переводе в другую клинику.

## 22. Stage 1 — фактическая реализация

### 22.1. Схема (v9 → v10 на исходной линии; v26 → v27 после интеграции)

Таблица `patient_portal_access`, одна строка на карточку:

| Колонка | Тип | Назначение |
|---|---|---|
| `patient_id` | PK, FK → `patients(id)` ON DELETE CASCADE | карточка-владелец |
| `email_normalized` | TEXT NOT NULL **UNIQUE** | нормализованный адрес; UNIQUE выражает «один email — одна карточка» |
| `status` | CHECK (`linked`/`active`/`revoked`) | Stage 1 достигает только `linked` и `revoked` |
| `linked_at`, `linked_by_user_id` | | кто и когда выдал |
| `activated_at`, `enrollment_state`, `last_login_at` | | **Stage 2**; Stage 1 их не пишет |
| `revoked_at`, `revoked_by_user_id` | | след отзыва |
| `updated_at` | | конвенция остальных таблиц |
| CHECK | `status <> 'revoked' OR revoked_at IS NOT NULL` | отзыв нельзя записать без отметки времени |

Отклонения от предложения §4.2 и их причины:

- `patient_id` сделан первичным ключом, а не отдельным `id` — так устроена соседняя `patient_notification_preferences`, и это сразу запрещает две записи доступа на одну карточку.
- Добавлены `revoked_at`/`revoked_by_user_id` и `updated_at`: без них отзыв нечем подтвердить, а `updated_at` есть у всех сопоставимых таблиц.
- `status = 'active'` объявлен в CHECK заранее: его выставит Stage 2 при первой успешной активации. В SQLite изменить CHECK позже можно только пересборкой таблицы — дешевле объявить значение сейчас, чем мигрировать потом.
- Колонки Stage 2 созданы пустыми намеренно: это места под будущие данные, а не работающая функциональность. Stage 1 их не заполняет ни при каком сценарии.

Миграция — `migrate_v9_to_v10`: только `CREATE TABLE IF NOT EXISTS` через `SCHEMA_SQL`, без изменения `patients` и без backfill. Существующая карточка без строки = нет мобильного доступа, что и есть верное состояние.

> Интеграция `integration/combined-preaudit`: на линии исправлений номера v10…v26 заняты миграциями консилиума, целостности медицинских записей и реестра дублей. Поэтому миграция мобильного доступа перенесена как аддитивный шаг `migrate_v26_to_v27`; база, записанная этой сборкой (v10 с таблицей `patient_portal_access`), доводится до v27 общей цепочкой без потери строк, а ее резервные копии принимаются как сборка `portal-a3fbe00`.

### 22.2. Права

Новой роли нет, новой стратегии scope нет. Добавлены две функции поверх существующих проверок:

```
can_manage_portal_access = role in (developer, department_head) AND can_write_patient
can_revoke_portal_access = can_write_patient
```

| Операция | developer | department_head | doctor | deputy_chief_oncology / caop_head |
|---|---|---|---|---|
| Посмотреть статус | да | в своём scope | свои пациенты | да, только чтение |
| Привязать / изменить email | да | в своём scope | **нет (403)** | нет (403) |
| Отключить доступ | да | в своём scope | **свои пациенты** | нет (403) |

Пациент вне scope даёт 404, а не 403: существование чужой карточки не подтверждается.

### 22.3. Endpoints

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/patients/{id}/portal-access` | статус + флаги `canManage`/`canRevoke` |
| PUT | `/api/patients/{id}/portal-access` | привязать или сменить адрес |
| DELETE | `/api/patients/{id}/portal-access` | отключить доступ |

Все три — под существующей аутентификацией сотрудника и CSRF, по тем же конвенциям, что и остальные вложенные endpoints пациента. Patient-facing endpoints не добавлены.

### 22.4. Безопасность

- Адрес нормализуется (trim + lowercase) до валидации и до записи; UNIQUE работает по нормализованному значению.
- Занятый адрес даёт 409 с текстом, не называющим ни пациента, ни адрес.
- Отозванная строка сохраняет адрес: отозванный email нельзя тихо увести на другую карточку.
- Повторная привязка сбрасывает `enrollment_state`, `activated_at` и `last_login_at` — прежний enrollment относился к прежнему состоянию доступа.
- В интерфейс адрес отдаётся только маскированным (`p••••••@example.com`); полный адрес не покидает сервер.
- Аудит: `portal_access_linked`, `portal_access_email_changed`, `portal_access_revoked`. В `detail` только статусы и флаг «адрес менялся». Ни адреса, ни телефона, ни ФИО, ни медицинских данных. Отказ по правам пишется существующим `access_denied` с `action=portal_access_manage` / `action=portal_access_revoke`.
- Мобильный доступ не входит в экспорт пациентов: это управление доступом, а не медицинские данные.

### 22.5. Что намеренно не реализовано

OTP, доставка почты, TOTP, recovery-коды, patient-сессии, доверенные устройства, patient-facing API, messaging, документы, расписание, каталог. Мобильное приложение не изменялось: разрешение `INTERNET` не добавлено, сетевого слоя по-прежнему нет.

**Доставка OTP не реализована потому, что Stage 2 требует отдельного решения по SMTP/провайдеру.** Код не содержит ни фиктивной отправки, ни заглушки провайдера — вместо этого в сервисе есть единственный шов `portal_access.activation_allowed(row)`, который Stage 2 обязан спрашивать перед выдачей OTP.

### 22.6. Блокеры Stage 2

1. Почтовый провайдер и канал доставки не выбраны. В системе существует только канал `sms` с mock-провайдером; для email нужен новый канал, конфигурация и согласование.
2. Решение по объёму медданных для мобильного приложения (§18, п. 2) — нужно до patient-facing сериализатора.
3. Транспорт patient-сессий (Bearer вместо cookie+CSRF) требует отдельного проектного решения: существующий механизм сессий привязан к `users.id` и к cookie.
