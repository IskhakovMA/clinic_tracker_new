# ADR-MFA-CONTINUITY-002, версия 2.0 — C + S1

Статус: **предложение, требует отдельного утверждения перед изменением WP-F**. Дата: 31.10.2026. Исходный WP-F pending/permit **v1 не изменен**. Предложенный номер версии не является уже существующим форматом файла или миграцией.

## Решение и граница доказательства

C допускается лишь для зарегистрированной до начала обслуживания штатной verify/migrate-операции, с независимым актуальным security-anchor до и после, эксклюзивными блокировками, успешной offline-проверкой и неизменной нормализованной security-проекцией. Новый generation сам по себе ничего не доказывает. Любой restore, rollback, неизвестное происхождение, неполное завершение или потеря свидетельства → S1 SECURITY_REVIEW_HOLD. Повторный verify не снимает эту метку.

Security-проекция включает UUID установки/сотрудников, случайные user_handle, owner/credential ID/public key/алгоритм, активность и tombstones факторов, BE/BS/counters, auth_epoch/парольную ревизию/статус и назначение recovery-операторов, использованные/отозванные recovery-хэши, открытые challenges/claims/grants, assurance/policy и security-relevant сессии. Нельзя исключать поле ради совпадения. Миграция с разрешенными преобразованиями требует заранее утвержденного versioned mapping с доказательством сохранения семантики; текущая модель разрешает только точное равенство проекции. Клинические таблицы не превращаются в источник MFA-доверия.

**Неустранимая граница:** старая база + старые sidecars + старый подписанный ledger неотличимы от прошлого легитимного состояния без внешнего актуального свидетельства. Подпись доказывает авторство, а не свежесть. Хэш в восстановленной базе не решает проблему. Отдельный файл на том же сервере, который откатывается тем же администратором, недостаточен.

## Требуемая будущая граница доверия

Независимо администрируемый current witness с аутентифицированными запросами, durable монотонным sequence и CAS/эксклюзивной reservation установки. Он хранит актуальные security mutations/высокие отметки epoch, tombstones и одноразового расходования; сохраняет BEGIN/END происхождение обслуживания. Его журнал не входит в клинический restore-set. Клиенты проверяют freshness онлайн, а не принимают произвольный старый receipt. При недоступности, несогласованном восстановлении самого witness, split-brain, потере ключей/истории — S1. Катастрофа witness требует отдельной процедуры восстановления доверия, а не копирования старого ledger.

Не выбран сервис, хранилище, домен или реальный ключ. `Witness` в `prototype/final_model.py` — **локальная SQLite-заглушка этой внешней границы**, не безопасный production ledger, не distributed consensus и не доказательство защищенности от root. Она сознательно размещена вне моделируемого restore-set. Сетевой протокол, подписи receipt, защита журналов, безопасное восстановление witness и live MFA mutation integration пока не реализованы.

## Будущий порядок протокола (требует WP-F v2)

1. Под эксклюзивными maintenance/auth блокировками исключить новые security changes и проверить текущий witness/permit/UUID/schema/security projection. Внешний witness durable фиксирует BEGIN: operation, operation UUID, pre-generation, pre-sequence, pre-digest, допустимую миграцию и состояние PENDING_C либо S1. Без подтвержденного BEGIN изменения запрещены.
2. Durable local pending публикуется до первого изменения БД: приватный temp, fsync файла, atomic rename, fsync каталога. Ошибка любого шага означает отказ и S1/незавершенный BEGIN. Старый permit не имеет приоритета.
3. Только доверенный CLI определяет происхождение операции; имя операции не принимается от HTTP-клиента или из восстановленной базы. Restore помечается S1 ДО замены даже идентичной базы. Все пути записи/worker/startup подчинены общему допуску, включая lifespan off.
4. Обслуживание + обязательный offline verify; проверка точной security-проекции и WP-C/WP-F-инвариантов. Exit 0 restore все равно S1. Exit 1/3 после начала, SIGKILL и неизвестное состояние не могут быть «отмыты» verify. Даже no-op migrate имеет историю BEGIN/END.
5. Для C сначала подготовить строго связанный receipt (sequence, operation UUID/type, installation UUID, до/после generation, schema, security digest, policy/version mapping). Публикация локального cache с fsync файла/каталога еще **не** разрешение. Только после ее подтверждения witness CAS завершает конкретную reservation. Затем свежий witness и локальный receipt должны совпасть при каждом допуске. Потерянный ответ finalize — диагностика witness и fail-closed; не повторная выдача вслепую.
6. S1 может быть разрешен только отдельной утвержденной security review/reproof ceremony с актуальной историей/перепривязкой, новыми epochs и уничтожением восстановленных sessions/flows/grants/codes. **В прототипе команды очистки S1 нет.** Offline verify выдает DB admission, не MFA assurance.

Атомарная видимость rename и долговечность различаются: видимый receipt после неуспешного directory fsync не является разрешением. BEGIN остается незавершенным у witness. Обычная перезагрузка при полностью подтвержденной паре не требует ручной проверки; незавершенная операция требует review. Плановый backup не меняет trust.

## Crash-матрица

| Точка/состояние | Результат |
|---|---|
| До durable BEGIN / ошибка записи BEGIN | Изменять БД запрещено; старый подтвержденный допуск допустим лишь если обслуживание действительно не началось |
| BEGIN подтвержден, local pending еще нет | Witness блокирует; SIGKILL не возвращает доверие |
| fsync файла/rename/fsync каталога pending/receipt не подтвержден | Нет доказательства долговечности; fail-closed |
| После замены БД, exit 3 или SIGKILL | Незавершенная reservation/S1, verify не переносит доверие |
| Обычный verify, no-op migrate, проверенная миграция | C только при полном BEGIN/проверке равенства/END |
| Restore exit 0 либо аварийный restore | Всегда S1, даже с совпавшим digest |
| Старая БД и старые sidecars | Актуальный независимый sequence/security-state не совпадают; S1 |
| Отозванный ключ/использованный код/старый auth_epoch вернулись | Сравнение с актуальным witness отказывает |
| Два конкурирующих BEGIN / несовпадение nonce | Консервативный hold, не два допуска |
| После durable receipt, до END / потеря ответа END | Доступ только при свежем подтвержденном witness; иначе hold |
| Откат самого witness вместе с приложением | Не покрывается локальной моделью; инфраструктурный блокер для C |

Тесты моделируют реальные child-process SIGKILL в пяти точках публикации, реальные ошибки os.fsync, rollback транзакции и durable witness pending. Реальное отключение питания, честность контроллера диска, Linux filesystem/VFS и удаленный witness не квалифицированы. Различие описано SQLite: [Atomic Commit](https://www.sqlite.org/atomiccommit.html), [synchronous/WAL](https://www.sqlite.org/pragma.html).

## Совместимость

v1 остается строгим и неизменным. v1 permit не служит доказательством C; первый переход — security hold и отдельная ceremony. Версия протокола обслуживания независима от schema v31. Нельзя односторонне развернуть v31 с полями v2, читаемыми старыми worker/CLI. Нужны согласованные версии всех writers/readers, запрет downgrade, backup/restore compatibility, native Linux fault matrix и отдельное ревью. Если независимый witness не утвержден, единственный допустимый режим — консервативный S1; RTO включает повторную проверку сотрудников.
