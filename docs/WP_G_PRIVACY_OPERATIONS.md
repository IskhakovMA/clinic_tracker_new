# WP-G этап 1: проверка перед эксплуатацией

Этап реализует технические ограничения. Он не подтверждает готовность хоста к production. MFA сотрудников в этом этапе отсутствует; AUD-28 закрыт лишь в части idle/password. WebAuthn/passkeys — направление следующей фазы, не действующий второй фактор.

## AI: по умолчанию никакой сети

Разрешение функции AI, разрешение данных и allowlist назначения независимы. `CLINIC_AI_DATA_MODE=disabled` и пустой `CLINIC_AI_SYNTHETIC_ALLOWLIST` блокируют сетевые обращения. Автообнаружение localhost не дает права обрабатывать реальные медицинские данные.

Для изолированного синтетического стенда требуются одновременно `CLINIC_ENV=local|test`, `CLINIC_AI_DATA_MODE=synthetic`, разрешенная AI-функция и точный base URL в `CLINIC_AI_SYNTHETIC_ALLOWLIST` (origin с портом + API-prefix). Пример исключительно для заглушки на тестовом стенде: `http://127.0.0.1:1234/v1`. Внешние HTTPS-адреса не заработают даже при добавлении в этот список: утвержденного remote-контракта и реального назначения нет. Старая переменная AI_ALLOW_INSECURE_TRANSPORT не является обходом. Прокси из окружения не используются.

Transport соединяется непосредственно с проверенным IP, проверяет peer, не выполняет повторного DNS lookup при connect, сохраняет TLS hostname/SNI/certificate checks. Redirects и автоматические повторные POST отсутствуют. DNS проверяется заново на каждом новом соединении. Loopback — отдельный synthetic режим; private/link-local/mapped/numeric aliases не становятся remote-разрешением.

На границе реального сетевого провайдера используются структурированные сообщения и временные aliases, привязанные к сессии/access context. Произвольные message/history, ФИО, постоянные IDs, контакты, диагнозы и свободные комментарии не уходят в wire DTO. Сейчас не утверждены даже минимальные клинические категории для remote; выдаются лишь opaque references. Это диагностический synthetic-контракт, а не разрешение отправлять реальные ПДн. Встроенные локальные операционные ответы сохраняются в разрешенной области UI. Не включать синтетический режим на реальной установке и не считать название environment доказательством синтетического происхождения базы.

## Аудит выдачи и его емкость

Перед выдачей чувствительного ответа фиксируются audit event и manifest одной транзакцией. Manifest содержит типы и IDs объектов, SHA-256 сериализованного ответа и access-context; он не содержит значения медицинских полей. Для агрегатов фиксируются также IDs вкладчиков, захваченные при вычислении, а не перечитанные после ответа. Отказы координируются общим слоем; старые best-effort denial events сохраняют тип/субъекта/объект и становятся частью атомарной записи. Неизвестные неканонические attempted IDs хэшируются, чтобы путь запроса не стал каналом хранения ФИО. Существующий обязательный экспорт не получает второй release event, но сессия/контекст проверяются перед выдачей результата повторно.

Событие означает разрешенную выдачу snapshot, а не получение/прочтение клиентом. Сбой аудита/manifest запрещает медицинское тело; неработающая БД может сделать запись самого отказа невозможной — это не основание пропустить данные.

Просмотр журнала и `GET /api/audit/{event_id}/manifest` доступен только can_view_audit. Просмотр также учитывается без рекурсивного чтения журнала самим аудитом. Медицинские WP-C события и их триггеры сохраняются. Manifest append-only. Новая автоматическая очистка НЕ включена: audit-prune пропускает все родительские события с manifest. Политику удержания/удаления и емкость необходимо отдельно утвердить; будущая процедура должна удалять согласованную пару, не ломая удержание медицинской истории.

Нет нового искусственного ограничения числа пациентов или пагинации. Техническая граница — действующий SQLite limit длины строки с запасом на служебные поля; превышение — явный fail-closed отказ, без усечения. Синтетические объемы 100/1000/10000 не заменяют расчет production-нагрузки. Учитывать O(N) manifest, WAL, индексы, число загрузок и бэкапы. До включения мониторить емкость и lock latency; срок хранения и автоматическое удаление не выбирать по одному бенчмарку.

## Сессия и пароль

Пилотная политика: 15 минут неактивности, отдельный absolute TTL по умолчанию 8 часов. Серверные UTC-часы — источник истины. Сначала проверяются сроки, затем активность. Истекшая сессия не возобновляется. Необычное будущее last_seen/откат часов дают отказ. Polling уведомлений, health, AI status и /auth/me не продлевают срок.

`POST /api/auth/activity` требует действительной сессии, контекста WP-D и CSRF, ограничен по частоте. Клиент отправляет его только при доверенном интерактивном событии; синтетический interval не продлевает сессию. Активное заполнение формы учитывается, без отправки значения поля. Локальный UI timer использует серверный remaining interval с консервативным учетом длительности запроса; медицинский доступ все равно проверяет сервер. Активность общая для cookie-сессии вкладок. Смена личности/полномочий и устаревшие ответы обрабатываются механизмами WP-D.

Перед пишущей транзакцией и commit медицинской операции сессия проверяется повторно. Срок, истекший во время ожидания блокировки/операции, не позволяет сохранить изменение. Для обычных медицинских routes повторно проверяется access context; import/transfer сохраняют собственную свежую проверку полномочий под lock. Реавторизация не пишет черновик: свежая карточка берется с сервера, несохраненное поле хранится отдельно с исходной версией, ручной старый draft получает 409. При утрате доступа/смене сотрудника старые данные удаляются по WP-D.

Новые/сменяемые пароли: минимум 15 символов, локальный blocklist, Argon2. Длинные фразы, paste и менеджеры паролей разрешены; верхняя граница API 200 символов сохраняется. Нет новых классов символов, календарной смены, массового сброса и запросов паролей/хэшей внешним сервисам. Старые хэши продолжают проверяться до смены пароля.

## Чек-лист инфраструктуры — заполняет оператор

До production владелец фиксирует дату, исполнителя, проверяющего, хост/носитель и подтверждающий документ. Значения этой работой не заполнены.

| Объект | Что проверить и сохранить как доказательство |
| --- | --- |
| DATA_DIR | Реальный зашифрованный том, включая DB/WAL/SHM/journal и технические снимки; статус FileVault/шифрования Linux/ключей по принятой процедуре хоста |
| Сервисный аккаунт | Отдельный непривилегированный владелец, private DATA_DIR, ограничения ACL/других пользователей, отсутствие лишних writers и диагностических копий в общих папках |
| Временные файлы | Private-каталоги на томе данных; не системный общий temp/не внешняя реплика для plaintext; ENOSPC/права/SIGKILL и перечень orphan-файлов |
| Резервные копии | CTBK verification + пробное восстановление; отдельное хранение/ротация/доступ к ключам; реплики/snapshots и их политики. Шифрованный CTBK НЕ доказывает шифрование live DB |
| Память/остатки | Swap, hibernation, core/crash dumps, диагностические пакеты; шифрование/ограничение доступа и установленная политика их сбора |
| Клиентские выгрузки | Браузер Downloads, рабочие станции, синхронизация, почтовые/общие папки и копии получателей. JSON/CSV/XLSX не шифруются подписью и могут попасть в swap |
| HTTPS/прокси | Реальный доверенный origin/сертификат, Secure/HSTS, ограниченный proxy peer, передача X-Clinic-User/X-Clinic-Access, обновление старых вкладок |
| Эксплуатация | Утвержденные RPO/RTO, backup cadence/retention/off-host, операторы/recovery drills, емкость read-audit, мониторинг и реагирование |

Ни шифрование хоста, ни systemd/cron, ни внешние хранилища/провайдеры этим этапом не устанавливаются. Полное шифрование диска защищает от офлайн-доступа, а не от скомпрометированного работающего аккаунта сервиса.

## Логическая очистка и носитель

`secure_delete=ON` уменьшает остатки обычных удаляемых SQLite строк после записи соответствующих страниц; старые WAL frames могут оставаться до штатного checkpoint. Checkpoint/VACUUM меняют файлы и не запускаются автоматически этим этапом. Рабочие соединения не переключены на secure_delete ради обещания стирания: это потребовало бы отдельного rollout после оценки I/O, а физическую гарантию все равно не дает. Медицинская append-only история WP-C остается неизменной и неудаляемой прежними правилами.

Обычный успех/failure backup очищает свой private temp через finally. SIGKILL не выполняет finally: открытый snapshot может остаться с private правами. Не удалять его без offline-инвентаризации и подтвержденной процедуры. Не удалять WAL/SHM, recovery/quarantine/pending/permit «для запуска». Технические маркеры допуска не являются копиями медицинских данных и не чинятся удалением.

Любое одобренное обслуживание самой базы (включая будущую cleanup-команду) соблюдает WP-F: исключительные блокировки, проверенная recovery copy, durable pending ДО мутации, отдельная проверка оператора `verify-db --confirm-offline`. Успешный rename или exit 0 не разрешают запуск автоматически. Код этой фазы не добавляет новую возможность физического удаления медицинской истории.

SQL DELETE, secure_delete, VACUUM, TRUNCATE WAL и unlink НЕ гарантируют физического стирания SSD, снапшотов и резервных копий. Для списания:

1. Утвердить основание и сроки хранения, проверить обязательное удержание клинической истории, назначить оператора и проверяющего.
2. Инвентаризировать все экземпляры: база/sidecars/temp, exports, snapshots, backup/replicas, key escrow и клиентские загрузки. Зафиксировать прекращение доступа.
3. Выбрать подтверждаемый для данного носителя метод sanitization/cryptographic erase либо физическое уничтожение. Crypto-erase возможен только при доказанной полноте шифрования и уничтожении всех доступных экземпляров ключа.
4. Учесть копии и ключи отдельно; не уничтожать единственную исправную recovery-копию без утвержденного решения. При старом restore ранее удаленные данные могут вернуться — нужен утвержденный порядок повторного применения ограничений.
5. Проверить результат допустимым методом, оформить акт с идентификатором носителя, методом, временем, ответственными и доказательствами, без ПДн. Никаких destructive-действий на реальных дисках в рамках WP-G.

Технические ориентиры: [SQLite secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete), [WAL](https://www.sqlite.org/wal.html), [NIST SP 800-88 Rev.2](https://csrc.nist.gov/pubs/sp/800/88/r2/final). Они не подтверждают фактическую конфигурацию конкретного хоста.

## v30, обновление и второй этап

Миграция v29→v30 явная; read manifests и защитные триггеры добавляются без изменения медицинских значений и версий. Проверенная pre-migrate копия, pending/permit v1 и offline verify сохраняются. Старые зашифрованные копии проходят прежнюю строгую идентификацию/восстановление; в каталог добавлена точная структура одобренного WP-F v29 из git archive, не перезаписана историческая схема v29. Обычный startup не мигрирует и не выдает допуск.

Перед MFA нужны решения: реальный HTTPS origin/RP ID; обязательные роли и rollout; device-bound/synced passkeys; резервный фактор; recovery и emergency-доступ; подтверждение личности/операторы/поддержка; отзыв сессий и проверка браузеров/устройств. Парольный reset не должен стать обходом будущего MFA. SMS/email не подключаются. До реализации/проверки второго фактора AUD-28 полностью закрытым не объявляется.
