# Система планирования — бриф для продолжения работы

Актуально на 2026-07-31, после UI/UX-редизайна и полировки (этапы 4–5). Описывает **текущее рабочее
приложение**. Функциональная история трекера — в `PROJECT_BRIEF.md` (осторожно: он описывает
архитектуру до появления бэкенда, см. «Что устарело в основном брифе»).

## Что это сейчас

Локальное клиент-серверное приложение для ведения маршрута онкопациентов:

```
index.html          канонический entrypoint — единственная страница
static/styles.css   вся вёрстка и обе темы оформления
static/app.js       весь фронтенд-код (объект app, ~3300 строк)
static/fonts.css    IBM Plex Sans/Mono, встроены base64
static/logo.png     логотип МКНЦ
backend/            FastAPI + SQLite + Pydantic + Argon2id, 155 pytest-тестов
docs/screenshots/   16 скриншотов (8 тёмных + 8 светлых)
```

Запуск, команды обслуживания и восстановление данных — в `README.md`.
Модель безопасности, что проверено и какие ограничения остались — в `SECURITY_AUDIT.md`.
Токены, компоненты, темы, адаптивность и доступность — в `DESIGN_SYSTEM.md`.

**Важно для следующей сессии**: приложение открывается **только через бэкенд**
(`http://127.0.0.1:8420/`). Файл `index.html` сам по себе не работает — двойной клик
даст пустую страницу. Данные пациентов лежат в SQLite (`backend/data/clinic.db`),
в браузере хранится только выбранная тема.

## Как проект пришёл к текущему виду

**Этап 0 — функционал** (см. `PROJECT_BRIEF.md`): один автономный HTML-файл, данные в
localStorage, клиентский логин-гейт с общим паролем `'password'` в исходнике.

**Этап 1 — первый редизайн**: новый визуал применён поверх копии `clinic.html`, вся
JS-логика сохранена. Тогда же прошёл первый security-аудит: найден и исправлен stored/DOM
XSS через несанированный вывод полей пациента (`escapeHtml()` в 23 точках) + правки
доступности.

**Этап 2 — бэкенд** (промт `propt (1).docx`, ветка `feat/secure-clinic-backend`): FastAPI +
SQLite + Pydantic. Пароль и список пользователей удалены из клиентского кода, авторизация
серверная (Argon2id, серверные сессии, CSRF), медицинские данные переехали из localStorage в
SQLite, импорт переписан на строгую схему preview→подтверждение→транзакция, экспорт — только
после авторизации, добавлены security-заголовки. Экран логина упрощён до одного поля пароля —
**согласованное решение**: приложение однопользовательское, прежние три «учётки» были лишь
подписью в шапке и не разграничивали доступ.

**Этап 3 — hardening** (промт `propt (3).docx`, ветка `security/frontend-csp-hardening`):
устранены все ~44 inline `on*=`-обработчика, `innerHTML` (11 точек) заменён на
`createElement`/`textContent`/`replaceChildren`, функции `escapeJsAttr`/`escapeHtml` удалены
как ненужные, CSP запретила inline-скрипты (`script-src-attr 'none'`). Добавлены: обезличенный
журнал аудита (`audit_events`), инвалидация всех сессий при смене пароля, политика слабых
паролей, кроссплатформенные `check-db`/`backup`/`restore` через SQLite backup API.

**Этап 4 — UI/UX-редизайн** (промт `propt (4).docx`, ветка `feat/ui-ux-redesign`): по двум
присланным референсам (тёмный и светлый). Фронтенд разделён на `index.html` + `static/styles.css`
+ `static/app.js`; две полноценные темы с переключением без перезагрузки; новая структура —
сайдбар из 7 разделов, таблица пациентов, отдельный экран карточки с 8 вкладками; таймлайн,
формы, модалки и потоки импорта/экспорта переработаны; нативные `alert`/`confirm`/`prompt`
заменены доступными модалками с focus trap. Все стили вынесены в файл, из CSP убрано последнее
послабление `style-src 'unsafe-inline'`. Устаревшие `clinic.html` и `clinic-v2.html` удалены.

**Этап 5 — полировка** (промт `propt (5).docx`, та же ветка): продукт переименован в
**«Система планирования»** во всех видимых местах; прежний пользовательский label заменён на
**«Профиль клиентского пути»** (внутреннее поле `nosology` в API/БД сохранено ради
совместимости выгрузок); англицизмы («сводка» вместо старой кальки); команда администратора убрана
с экрана входа. Мобильный список пациентов перестроен: импорт/экспорт под кнопкой «Данные»,
фильтры и сортировка под «Фильтры · N», статистика 2×2 — список виден почти сразу. Контраст
доведён до WCAG AA расчётом (новые токены `--border-field` и `--accent-text`). Вкладки
карточки переносятся в две строки на узких экранах вместо скрытой прокрутки.

## Текущее состояние безопасности (кратко)

- CSP **без единого послабления**: ни `unsafe-inline`, ни `unsafe-eval`.
- `innerHTML` = 0, inline-обработчики = 0, inline-стили = 0 — закреплено тестами
  `backend/tests/test_frontend_csp.py`, которые падают при любой попытке их вернуть.
- Авторизация серверная (Argon2id + серверные сессии + CSRF), медицинские данные только
  в SQLite, действия пишутся в обезличенный журнал аудита.
- 155 тестов, `pip-audit` чистый.

## Что не менялось за все пять этапов

Вся предметная логика: структура данных пациента, регламентные сроки по профилям клиентского пути, чек-лист
обследований, каскадный выбор диагноза (локализация → МКБ-10), таймлайн из 7 этапов и переходы
между ними с фиксацией фактических дат, фильтры, сортировки, тайм-метки «Добавлено/Обновлено»,
сводка для отчётности. Менялись только видимые формулировки — данные и API те же. Справочники `icd10Localizations` и `nosologyData` перенесены в
`static/app.js` дословно. Формат данных пациента совместим со старым экспортом — JSON из
localStorage-версии импортируется (одноразовая миграция или обычный импорт).

## Что устарело в основном брифе (`PROJECT_BRIEF.md`)

Файл не переписывался и остаётся источником по функционалу, но эти утверждения больше не верны:
- «Единственный файл проекта… без сервера, работает полностью офлайн. Данные — в `localStorage`» —
  теперь бэкенд обязателен, данные в SQLite.
- Раздел «Доступ с телефона» (открыть файл в Safari) — неприменим: нужен доступ к запущенному
  бэкенду по сети, а это требует HTTPS reverse proxy (см. README).
- Упоминания демо-пациентов и `getDefaultPatients()` — функция удалена, база стартует пустой.
- Ограничение «клиентский логин с общим паролем» — исправлено на этапе 2.
- Описания вида «карточка пациента раскрывается в списке» — с этапа 4 карточка это отдельный
  экран с вкладками.

## Вопрос о двух дизайнах — закрыт

Прежний бриф держал открытым выбор между `clinic.html` (старый автономный вид) и `clinic-v2`.
На этапе 4 промт прямо потребовал убрать legacy-страницу из пользовательского потока, поэтому
**`clinic.html` и `clinic-v2.html` удалены** из проекта; сервер отдаёт на них 404. Актуальный
интерфейс — только новый, по референсам этапа 4.

Содержимое удалённых файлов остаётся в истории git (baseline `a5bcdfb` и ветки этапов 2–3).
Если понадобится посмотреть старый вид: `git show a5bcdfb:clinic.html > /tmp/old.html`.
Возвращать их в проект не следует — вместе с ними вернутся пароль в исходнике и хранение
медицинских данных в браузере.

## Технический побочный эффект

Node.js на машине не было — поставлен через `nvm` (стандартные строки в `~/.zshrc`) на этапе 1.
Сейчас используется только для `node --check static/app.js` в проверках; для работы приложения
не требуется. Python-окружение — `.venv` в корне проекта (в Git не попадает). На этапе 4 в venv
доустановлен `websocket-client` — им пользуется скрипт съёмки скриншотов через Chrome DevTools
Protocol, который живёт вне репозитория и в зависимости проекта не входит.

## Правила, которые нельзя нарушать при доработках

Закреплены тестами — если нарушить, `pytest` покраснеет:

1. Разметка строится только через DOM API (`el()`/`frag()`/`option()` в начале `static/app.js`).
   Никакой сборки HTML из строк, никаких inline-обработчиков и inline-стилей.
2. Динамические значения выражаются классами, а не атрибутом стиля (пример — полоса прогресса
   на 7 ступеней по числу этапов).
3. В `localStorage` можно писать только тему оформления. Медицинские данные и токены — нельзя.
4. CSP не ослаблять. Внешние ресурсы (CDN, шрифты, аналитика) не подключать.
5. Legacy-страницы не возвращать в раздачу.
6. Пользовательские тексты — по-русски и по согласованной терминологии
   («Система планирования», «Профиль клиентского пути», «сводка»); внутреннее
   поле `nosology` при этом не переименовывать. Технические команды администратора
   в интерфейсе не показывать — им место в README.
7. Контраст: текст ≥4.5:1, границы полей ≥3:1 в обеих темах (проверяется тестами
   `test_terminology.py`).

## Что дальше

Отдельной согласованной задачи сейчас нет. Возможные направления, если понадобятся:

- **Открыть PR-ы и слить ветки в `main`** — сейчас четыре ветки живут параллельно, `main` отстал
  на три этапа. Это стоит сделать раньше, чем начинать новый крупный этап.
- Даты рождения нет в модели данных — в карточке показывается только возраст (в референсе
  было «42 года, 15.03.1983»). Если нужно — это миграция схемы + поле в формах.
- Раздел «Календарь» сейчас производная витрина по плановым событиям; полноценного
  календарного представления (сетка месяца, перенос событий) нет.
- Подпись «что изменилось» в списке пациентов берётся из журнала аудита и потому огрублена
  («Обновлены данные»). Точнее — только если хранить историю изменений полей отдельно.
